# Gateway 1.5.x management contract

ACP Gateway is the engine. AgenLynk and other consumers render and invoke this contract; they must not independently implement execution, retention, provider or permission policy. API major remains 1 and state schema remains 5. New capability discovery is on **full** `setup`, leaving summary payload costs unchanged.

## Public boundary

Import `GatewayRpcClient`, `GatewayError`, `ERROR_CODES`, `GATEWAY_API_VERSION` from `acp-gateway-daemon/client` (the npm package and a source checkout). A runtime release that an app installs and mounts keeps the package name `acp-gateway`, so there the same four exports come from `acp-gateway/client`. No private engine imports are needed. `client.call(method, arguments, timeoutMs, {signal})` returns the RPC result or throws an error with stable `code` and optional `details`. A failed call is never evidence that an already-started worker did not execute; use the Task handle and idempotency key to reconcile.

`GatewayRpcClient({token, rootId, access: "control"|"observer", autoStart})` defaults to control for old consumers. Role is bound on the first authenticated request and cannot change on that connection. Observer uses the existing token, so this is server-enforced read-only behavior, **not** a separate credential boundary against an actor that possesses the control token.

Control socket: `ACP_GATEWAY_SOCKET`, else `acp-gateway-<uid>.sock` in the OS temporary directory, which is per user on macOS and usually the shared `/tmp` on Linux. The daemon binds it under umask 177, so it is created 0600 and never reachable by another user, not even for an instant. Since 1.8.0 the client checks, before it connects and again once connected, that the path holds a socket owned by the current user, and before it connects it also checks that the socket's whole directory chain — every component from the filesystem root down to the directory holding it — is owned by the current user or root and writable by no one else, unless a directory is sticky (a world-writable `/tmp` lets only an entry's own owner replace it). An `lstat` of the socket alone rejects a final symlink but follows an intermediate one, so a parent directory a stranger can replace with a link could point the connect at a foreign socket while both owner checks still saw the real one; a chain no other user can write is one no other user can redirect, which is what stands in for reading the connected peer's uid (there is no `LOCAL_PEERCRED`/`SO_PEERCRED` in Node without a native addon, which the Gateway does not ship). Otherwise the call fails with `SOCKET_UNTRUSTED` — `details: {socketPath, type, ownerUid, uid}` for the socket itself, `{socketPath, dir, …}` for an untrusted directory in the chain — before anything is written, the token included, and no daemon is started; `daemon_shutdown` and `shutdown_if_idle` report it too instead of `alreadyStopped`. The daemon makes the same directory-chain check before it touches anything at the path — its lock file, the probe and removal of a stale socket, the bind — and, rather than put its socket where another user could swap a link for it, refuses to start: it records `SOCKET_UNTRUSTED` in the recovery marker and exits with status 78. A socket directory that does not exist is not untrusted to a client, since nothing can be listening in it: the client sends nothing and takes it as no daemon, as it takes a missing socket, so `daemon_shutdown` and `shutdown_if_idle` return `alreadyStopped` and any other call autostarts the daemon. The daemon does not create the directory and refuses to start there as above, so that call reports `SOCKET_UNTRUSTED` from the recovery marker. The client and the daemon check one path only, the canonical one: each resolves the socket's directory as the kernel does, links and `..` included, and uses the socket's name in that real directory for the check, the connect and the bind alike, never the path as written, whose links the kernel would resolve again at each use, after whoever owns one could have pointed it elsewhere. It is the canonical path that has to fit in a Unix socket address: 103 bytes on macOS and 107 on Linux, counted in UTF-8, and on macOS a path in the temporary directory resolves 8 bytes longer, under `/private`. Some systems take no longer path, and Node does not refuse one there but cuts it short (Node 22 on macOS 14, and on Linux): a daemon would bind its socket at another path, and clients would find nothing at this one. Since 1.8.0 a canonical path over the limit fails with `SOCKET_PATH_TOO_LONG` — `details: {socketPath, canonicalPath, bytes, limitBytes}`, `socketPath` as configured — before anything is sent or bound: the client starts no daemon, and `daemon_shutdown` and `shutdown_if_idle` report it too instead of `alreadyStopped`; the daemon refuses to start, records `SOCKET_PATH_TOO_LONG` in the recovery marker and exits with status 78. The default path is well within the limit; keep a hand-set one short too. The default paths pass (a per-user temporary directory on macOS, a sticky `/tmp` on Linux); a hand-set `ACP_GATEWAY_SOCKET` in a directory group- or other-writable and not sticky is what this turns away. On Linux another user can still create the default path first and so keep the Gateway from starting; set `ACP_GATEWAY_SOCKET` to a path in a directory only you can write, such as `$XDG_RUNTIME_DIR/acp-gateway.sock`, for every client: the Control MCP entry, apps, `acp-gateway-admin` and the installer. Where there is no uid to compare (Windows) the check is skipped.

Control identity: the installer keeps the token and root id in `install.json` `identity.{token,rootId}` (`ACP_GATEWAY_INSTALL_STATE`, default `~/.acp-gateway/install.json`, mode 0600), and nowhere else. Since 1.8.0 the Control MCP entry it registers in an agent CLI carries neither, only `ACP_GATEWAY_INSTALL_STATE` when the file is not at its default path. The front door, like a consumer, takes each once, when it starts, from its environment (`ACP_GATEWAY_CONTROL_TOKEN`, `ACP_GATEWAY_ROOT_ID`) when set, else from that file; a token in neither is an error, a root id in neither falls back to `main-<ppid>` as before. A client that autostarts the daemon hands it the identity it holds (its own, else the one in its environment) as one JSON line on the daemon's stdin, and sets only `ACP_GATEWAY_IDENTITY_STDIN=1` in the daemon's environment: the OS keeps a process's initial environment readable by any process of the same user (`ps -E` on macOS, `/proc/<pid>/environ` on Linux), and the daemon's pid is in `<socket>.lock`. On Windows the identity still goes in the environment. A daemon started with `ACP_GATEWAY_CONTROL_TOKEN` set (by hand, by a supervisor, or by a consumer that launches it itself) takes the identity from there and never reads stdin, and then the token stays readable in that process's environment block. A daemon told to read stdin that gets no usable line there (none within 5 seconds, more than 16 KiB without a line end, or no token of at least 24 characters) exits with status 78 and records `DAEMON_IDENTITY_INVALID` in the recovery marker file, which the client reports. Either way the daemon removes the identity from its own environment, so no process it starts (Workers, terminals, adapter updates through npm or uv) inherits it, nor `ACP_GATEWAY_SOCKET` or a Main's session markers. Everything else in the daemon's environment, which comes from whatever started it (a client's autostart, a supervisor, a consumer), still reaches Workers and their terminals, API keys, cloud credentials and `SSH_AUTH_SOCK` included, so a provider that signs in through its environment keeps working; there is no allowlist. `acp-gateway-bootstrap --rotate-token` replaces the identity in the file only: a consumer that cached it must read it again, and a running daemon accepts only the identity it started with until it restarts.

Observer calls: setup without provider/refresh; session list/get; config list without worker restore; poll; task_get/list/result; inbox list/get/attention; subscribe/unsubscribe; gateway_config get; provider list; retention_preview. All other calls fail with `OBSERVER_ACCESS_DENIED`. Observer traffic never attaches owner presence or touches owner activity. Credentials are still required for every method except public guide.

## Engine settings

`gateway_config {action:"get"}` (default action) returns:

```json
{
  "ok": true,
  "revision": 0,
  "activeRevision": 0,
  "pendingRestart": false,
  "pendingLiveApply": false,
  "unsupportedLegacySettings": [],
  "options": [
    {
      "id": "idleUnloadMs", "group": "lifecycle", "type": "number",
      "environment": "ACP_GATEWAY_IDLE_UNLOAD_MS", "minimum": 0,
      "defaultValue": 1800000, "currentValue": 1800000,
      "configuredValue": 1800000, "storedValue": null,
      "source": "default", "editable": true,
      "requiresRestart": true, "pending": false
    }
  ]
}
```

The example shows one option; get returns the complete supported catalog. Number values are safe integers. Booleans are JSON booleans and enum options declare `values`. Unknown settings are rejected; arbitrary provider env, commands, secrets and recovery overrides are not exposed as writable settings.

`gateway_config {action:"set", expectedRevision:N, values:{...}}` stages settings. `gateway_config {action:"reset", expectedRevision:N, ids:[...]}` resets selected keys to defaults. Revision mismatch or ENV-locked keys fail with `CONFIG_CONFLICT`. Invalid values/cross-field budgets fail with `CONFIG_INVALID`; unsupported keys use `INVALID_ARGUMENT`. All settings currently require restart, including adapter update policy. Saving is not applying.

Precedence: environment > engine settings file > defaults. If the engine settings file does not yet exist, supported values from legacy `install.json.gatewayConfig` and `agentUpdates` substitute for stored values. The first successful write materializes them into settings.json without rewriting install identity, managed MCP, skill or UI settings. Unsupported legacy engine keys are reported. Once migrated, legacy changes are not imported again. CLI installer update-policy flags write through the same settings store.

Paths: `ACP_GATEWAY_SETTINGS` overrides the engine settings path. Otherwise it is `settings.json` next to `ACP_GATEWAY_INSTALL_STATE` (default `~/.acp-gateway/install.json`). Use explicit paths for isolated deployments. Writes use exclusive locks, fsynced private temporary files, rename and parent-directory fsync. A `CONFIG_BUSY` lock after a crash requires inspecting its recorded PID and confirming no writer exists before removing only that `.write.lock` file. The engine does not silently steal stale-looking locks.

## Providers

- `provider {action:"list"}` returns `{ok,providers}` including boolean `enabled` and installed adapter metadata.
- `provider {action:"set_enabled",provider:"claude",enabled:false}` persists engine policy and returns `{ok,provider,enabled}`. Off blocks **new registrations**, including external session_restore, before starting work and again at registration. Already registered sessions can continue and reconnect. Policy is read per admission, independent of cached worker clients.
- `provider {action:"install",registryId:"claude-acp",dryRun:true}` uses the official Gateway installer. Dry-run is the default; only explicit `dryRun:false` installs. The result is the installer action/warning envelope. Set an adequate RPC timeout for installation. Request cancellation cannot undo an external package-manager operation that already started. Enabling/disabling is a separate operation; installation preserves the current disabled list.

Consumer-owned npm/uv invocations or copies of provider resolver policy are unnecessary. Distribution verification and provider definitions remain in the engine's installer/registry implementation.

## Safe shutdown and applying settings

`shutdown_if_idle {}` rejects with `SHUTDOWN_BLOCKED`, `details.blockers` when active sessions, tasks, unanswered inbox records, pending session admissions, in-flight mutations, provider starts, maintenance or agent updates exist. A successful admission atomically closes mutation admission before acknowledging shutdown. Further mutations fail with `GATEWAY_DRAINING`. A blocked attempt restores admission.

`daemon_shutdown {}` now uses the same safe default. Since 1.5.2 the public client never autostarts a daemon for `daemon_shutdown` or `shutdown_if_idle`; with nothing listening (no socket at the path, or no directory for it) it returns `{ok:true, alreadyStopped:true}`. `daemon_shutdown {force:true}` is an explicit destructive override for trusted control clients. OS SIGTERM/SIGINT remain unconditional shutdown. Force can interrupt workers; it does not claim their external side effects were rolled back.

Since 1.8.0, whenever the Gateway ends a provider process (a shutdown, an idle unload, maintenance stopping a retired adapter generation, or a fatal transport error: a line from the provider over the frame limit, or a provider that stops reading its stdin), it sends SIGTERM, then SIGKILL if the process is still running 2 seconds later, and stops waiting 2 seconds after that. On macOS and Linux the provider is started in a process group of its own, and both signals go to that whole group, so what the provider started ends with it: an adapter that a launcher such as `npx` started, and that ignores SIGTERM and its closed stdin, no longer outlives the launcher, and the wait lasts until the group is gone. A process that left the group (its own session or group) is not reached. On Windows the signals go to the provider process itself. The terminals the provider opened are ended the same way, with the same SIGKILL fallback: on macOS and Linux each with its whole process group, on Windows the terminal process itself. Before, a provider got only the SIGTERM, so one that ignored it kept running, and what it had started was never signalled.

Consumer restart sequence: close automatic subscription clients; request safe shutdown; wait for old process/socket/lock to exit; select/start the intended runtime; reconnect and verify build identity and active settings. A successful shutdown is not itself a new runtime activation, and saving config does not restart either application or engine. Legacy 1.4 daemons do not enforce this new safe shutdown contract; require capability before presenting it as safe.

## Permission policy enforcement

`permissionPolicy` is enforced on what reaches the Gateway over ACP: file and terminal callbacks and `session/request_permission`. A worker that edits through its own tools without asking bypasses it. For `read_only` and `ask` sessions, the engine selects the worker's advertised `mode` value `read-only` on open and on every restore. When a provider is known to still edit inside its session roots without a request (Codex), `session_open`/restore put a `{level:"warning", code:"permission_policy_partial", provider}` alert first in `relevantAlerts`. Consumers must show it and must not present such a session as edit-proof. The alert is additive; its absence does not certify complete enforcement for other providers.

Since 1.5.2, automatic decisions also depend on paths:
- The engine compares every path a request names (`toolCall.locations[].path`, and `file_path`/`path`/`notebook_path` in `rawInput`) with the session roots, resolving symlinks. Since 1.8.0 every path a Worker names, the files and working directory an approval is bound to, a terminal's working directory and the session roots are all resolved by the system realpath, with nothing lexical before it: a `..` after a link applies where the link leads, as the kernel resolves it, and on a case-insensitive macOS volume a path takes the letter case on disk. An approval, the write or terminal it covers and the root check therefore compare one spelling of a file or directory, however the Worker spelled it.
- A path outside the roots is never auto-approved. `read_only` refuses it. `auto_approve` sends it to Main as a normal pending permission request.
- Gateway-protected paths are refused under every policy, including `ask`, and are never shown to a human. They are `~/.acp-gateway`, the install/settings/state directories, and the control socket. Since 1.8.0 they also include, wherever they are, the provider definitions the Gateway reads (`ACP_GATEWAY_PROVIDERS`), whose commands a provider start runs, and the official registry cache (`ACP_GATEWAY_REGISTRY_CACHE`), whose packages an install takes; and, when `install.json`, the settings file or a state file is a symbolic link, the file it leads to, one that does not exist yet included, by its canonical path. `fs/read_text_file`/`fs/write_text_file` refuse them even inside a root.
- Since 1.8.0 `fs/read_text_file` and `fs/write_text_file` open the file once and read or write only through that descriptor. The open refuses a symbolic link as the last component (on macOS anywhere in the path) and anything but a regular file, such as a FIFO or a directory. After it, the path must still resolve to the checked location and to the opened file; on Linux the descriptor's own path (`/proc/self/fd/<fd>`) is compared as well, and a lookup there that fails for any reason but a missing `/proc` (a `/proc` mounted but unreadable, or a path longer than `PATH_MAX`, which a Worker can produce with a link to a deeply nested directory) refuses the read or write. Only a host without `/proc` goes without that comparison. A Worker that renames or symlinks inside its roots therefore cannot redirect the operation between the check and the open, and a write empties the file only after that check. Every check so far is about names, and a hard link is a second name for the same file: link(2) needs no read permission on its target, so a Worker can give a protected file a name inside its roots (`ln ~/.acp-gateway/install.json ./notes`). So the opened descriptor is also compared, by device and inode, with every regular file directly inside a protected directory (the token in `install.json`, and the engine settings and state kept beside it), a symbolic link there by the file it leads to, with every protected path that is itself a file, and with every artifact the Gateway keeps (below), and a match is refused, for reads and writes alike, before a byte is read or the file is emptied. A protected path or a file directly inside one that the Gateway cannot stat, or a protected directory it cannot list (a mode or an I/O error hiding them), refuses the open as well, since it could be that file; only a path that does not exist is skipped. A write to a dangling symbolic link, which used to create the link's target wherever it pointed, is refused. A write that creates the file creates it only in the directory the check approved, on macOS and on Linux with `/proc`. On macOS the open itself refuses a link anywhere in the path. On Linux, where the open refuses a link only as the last component, a write first opens the checked parent directory, requires that descriptor's own path (`/proc/self/fd/<fd>`) to be the checked one, and creates the file through it (`/proc/self/fd/<fd>/<name>`), which the kernel resolves to the held directory whatever has since been swapped in at its path; a parent already swapped for a symbolic link is refused before anything is created. The parent is held with `O_PATH`, which needs no permission on the directory itself, so a parent the daemon may write into and search but not list (mode `-wx`) still takes a new file; only a kernel that refuses `O_PATH` gets an open for reading, which needs the directory to be listable too. Elsewhere — Linux without `/proc`, and other systems — the open still follows a directory above the file swapped for a symbolic link between the check and the open, so a write that creates the file can create it, empty, where the link points, before the descriptor check refuses the write. The Gateway does not remove that file, and a refused write never deletes anything: Node has no `unlinkat`, so an unlink goes by name, and the same swap could redirect it onto a file that already existed, `install.json` included. The content and the truncation only ever go through the verified descriptor in any case, so nothing is written to that file and no existing file is emptied.
- Since 1.8.0 `fs/read_text_file` also judges a file by what it holds: a read whose text would contain the Control token the daemon accepts is refused before anything is returned, with an error that says the file holds a Gateway credential and nothing of its content. The checks above go by name and inode, and a copy of `install.json` (or of any file holding the token) inside the roots passes them, as does a hard link a Worker made to `install.json` whose old file the installer could not empty when it replaced it (below). Only the text a read would return is judged, so a window (`line`, `limit`) that does not contain the token is served, and `fs/write_text_file` is not affected.
- Since 1.8.0 a file the Gateway replaces by rename inside a protected directory is emptied once the rename succeeded, when a hard link still holds it: `install.json` on every installer write (the first identity, each entry recorded as it is rewritten, `--update`, `--rotate-token` and the end of a run), the engine settings and provider definitions, and the state snapshot. A rename replaces a name, not a file, so a hard link made to the old file (link(2) needs no permission on it) would otherwise keep its content, the token or the state, on an inode no longer inside the protected directory. The old file is opened before the rename, never through a symbolic link (a link at the path is replaced, and the file it leads to is left alone), and truncated through that descriptor only after the rename succeeded and the path names another file, and after the directory fsync where the write makes one; a rename that fails empties nothing. A replaced file no other name holds is not emptied: no one can reach it, and a reader that opened it before the rename still reads it whole, as before. A file the Gateway may not open for writing is replaced without being emptied, and on Windows, which has no open that refuses to follow a link, no replaced file is emptied; a read of such a link through the Gateway is still refused when it holds the token (above). The write-ahead log is not replaced this way: a rotation renames it aside on purpose until a synced snapshot covers it, then deletes it. A retired segment that a hard link still holds is emptied before it is deleted, and so is every other such file the Gateway deletes (a forensic copy of a damaged state file past its retention, a temporary a dead writer left beside the state, the settings or `install.json`, a migrated v4 `state.json`), so the link keeps nothing; one no other name holds is only deleted.
- Since 1.8.0 artifacts (`~/.acp-gateway/artifacts`, a level deeper than the walk above) are refused by inode too: the Gateway keeps the device and inode of every artifact it writes or finds at startup until it deletes the file, and refuses a `fs/read_text_file` or `fs/write_text_file` whose descriptor is one of them, under any name, before a byte is read or the file is emptied. An artifact the Gateway deletes (a superseded spill, or one past retention) that a hard link still holds is emptied before it is unlinked, so the link holds nothing; one without is only unlinked, and a reader that has it open still reads it whole.
- When several offered options share the chosen kind, a refusal prefers the one that lets the worker continue (for example Codex `decline` over `cancel`).

Commands are checked as well:
- A permission request's `rawInput.command` and a `terminal/create` command line are refused under every policy when they name a protected path, as an error and without a prompt. That covers the literal path and its `~`, `$HOME`, `${HOME}` and quoted spellings, plus any path-looking word that resolves physically into one, such as `link/../.acp-gateway`.
- Since 1.8.0 a word with a `.acp-gateway` path segment, relative or absolute, that resolves into no protected path is never decided automatically. It may name the protected directory from a working directory the checks cannot see, such as `.acp-gateway/install.json` after a `cd ~`, or be only a search pattern, such as `grep -rn ".acp-gateway" src`. Under `ask` it is a normal prompt. Under `auto_approve` it is not approved or run on its own: a permission request goes to Main as a normal pending request, and a `terminal/create` as a pending request with its full command. `read_only` refuses it.
- Other commands keep the policy's normal treatment. `auto_approve` trusts commands inside the roots, because a shell command's file access cannot be verified from its text. These checks are best effort: a variable, a glob or a script the Worker wrote can always hide a path, which is why Gateway terminals also run in a sandbox (below).

Since 1.8.0 a terminal the Gateway opens for a Worker (`terminal/create`) is kept off the protected paths by the OS, because the daemon starts it outside any provider sandbox:
- On macOS it runs under `/usr/bin/sandbox-exec` with a profile that allows everything except reading, writing or connecting to the protected paths: a directory with everything under it, a file or the socket by name, each by its real path. The terminal's pid, process group, exit status, output and `terminal/kill` are the command's own. Setuid programs such as `ps` and `top` cannot start inside the sandbox. A command that cannot start there, missing or setuid, exits with status 71 and sandbox-exec's `execvp() of '<command>' failed` line in its output; before 1.8.0 a missing command failed to spawn instead.
- Where no sandbox is available (Linux and other platforms, or a `sandbox-exec` that cannot apply a profile, as inside another sandbox), `auto_approve` no longer starts terminals on its own: each `terminal/create` becomes a normal pending permission request with its full command. Writes stay automatic.

Since 1.8.0 a `fs/write_text_file` or `terminal/create` waiting for Main names the operation, and an approval covers only what it named:
- The pending request's `toolCall` (`toolCallId: "client-<requestId>"`) is, for a terminal, `kind:"execute"`, `title:"Run: <command line>"` (one line, cut at 200 characters) and `rawInput: {command, args, cwd, env}`; for a write, `kind:"edit"`, `title:"Write <path> (<n> bytes)"`, `locations: [{path}]` and `rawInput: {path, bytes}`, without the content. Each `env` entry is `{name, value}` for a variable that decides what runs, and `{name}` alone for any other, whose value may be a credential the Worker passes along (a pending request is persisted). A variable decides what runs when it makes the loader, an interpreter, a shell or a common tool load or run code, or when the command line interpolates it (`$NAME` or `${NAME}` anywhere in the command or its args). The first kind are `PATH`, `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, `GCONV_PATH` and any `DYLD_*`; `NODE_OPTIONS`, `NODE_PATH`, `PYTHONPATH`, `PYTHONHOME`, `PYTHONSTARTUP`, `PYTHONUSERBASE`, `PERL5LIB`, `PERLLIB`, `PERL5OPT`, `RUBYLIB`, `RUBYOPT`, `GEM_HOME`, `GEM_PATH`, `BUNDLE_GEMFILE`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`, `CLASSPATH`, `LUA_PATH`, `LUA_CPATH` and `LUA_INIT`; `BASH_ENV`, `ENV`, `ZDOTDIR`, `PROMPT_COMMAND`, `SHELLOPTS`, `BASHOPTS`, `PS4` and any `BASH_FUNC_*`; `HOME` and `XDG_CONFIG_HOME`; `GIT_DIR`, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, any `GIT_CONFIG_KEY_*` and `GIT_CONFIG_VALUE_*`, `GIT_EDITOR`, `GIT_SEQUENCE_EDITOR`, `GIT_PAGER`, `GIT_PROXY_COMMAND` and `GIT_EXTERNAL_DIFF`; and `EDITOR`, `VISUAL`, `PAGER`, `MANPAGER`, `LESSOPEN` and `LESSCLOSE`. These are the common ones, not every one: a value shown only by its name is still compared when an approval is spent (below). A write or terminal that could not run anyway (outside the roots, protected, a cwd outside the roots, an `env` entry whose name or value is not a string, an `outputByteLimit` that is not a finite number of at least 1) is refused at once, before Main is asked and before anything is spawned or written.
- Main approving (`allow_*`) a Worker's `execute` request lets one later `terminal/create` through when it runs the same command, in the same working directory, with the same environment:
  - The command compares as an argv, word for word: the same number of words, each exactly the same. The approved command is `rawInput.command` or `cmd`. An array is the argv, and a string with `rawInput.args` is that string followed by the args. A string without args is a command line, and counts only when it is plain words: words separated by spaces or tabs, each either bare or wholly inside one pair of single or double quotes, which come off. Shell syntax (`;`, `&`, `|`, `<`, `>`, parentheses, `$`, a backquote, a backslash, `*`, `?`, brackets, braces, `~`, `=` or `#`), a quote that is not a whole word, an unclosed quote, or any blank other than a space or a tab makes the line opaque, and an opaque line, like a request that names no command, lets no terminal through. A `terminal/create` is the argv `[command, ...args]`. So a `sh -c` script, a login shell and a literal argv never stand in for one another: approving `["echo", "a; ./x"]` does not cover `sh -c "echo a; ./x"`, and approving `echo hi` covers the command `echo` with the argument `hi`, not `bash -lc "echo hi"`.
  - The working directory is the request's `rawInput.cwd`, or the session's when it names none, resolved like the terminal's, links included, and it must still hold the directory that was there when the request arrived, by device and inode. Another directory put at that path since, while Main decided included, is asked about anew, and so is a path that held no directory when the request arrived.
  - The terminal's `env` must hold exactly the variables of the request's `rawInput.env`, each with the same value. A terminal that adds, leaves out or changes any variable, whether Main is shown its value or only its name, is asked about anew: no list of the variables that make a program load code is complete, so the same `python3 -c …` with a `PYTHONPATH` the request did not carry is another command.
  - A command that uses indirect (`${!NAME}`) or arithmetic (`$((…))`, `$[…]`) expansion is never covered, since the variable that decides what runs cannot be named in advance: each such terminal is asked about.
- Approving an `edit`, `delete` or `move` request lets one `fs/write_text_file` through to each file it named (`locations[].path`, `rawInput.path`/`file_path`/`notebook_path`), resolved like the write when Main is asked, and bound to the regular file at that path when the request arrived, by device and inode, or to there being none. A later write to a path that now leads to another file is not covered, and is asked about anew: through a link re-pointed since, to a path whose file has been replaced (a hard link to another file put there included), or to a path where a file was put since there was none.
- A write is bound to its canonical target as resolved when the write arrived, the path Main is shown (`rawInput.path`): it opens that target, not the Worker's path resolved again, and is refused, with nothing written or emptied, when the Worker's path no longer resolves to it, when the file that was there has been replaced by another (another inode), or, where there was no file when the write arrived, when anything is at the path by the time the write opens it or the new file would not be created at that very path. Such a write creates its file exclusively, so a file put at the path meanwhile, a hard link to another file or a link included, is neither opened nor emptied; before, it was written to. A Worker that re-points a link while Main decides therefore gets an error that names only the approved path, and can send the write again.
- A terminal is bound the same way to its working directory as resolved when the `terminal/create` arrived, the canonical `cwd` Main is shown (`rawInput.cwd`). When it starts, the Worker's `cwd` must still resolve to that directory, and the directory there must still be the one that was there (the same device and inode). Otherwise nothing is started and the Worker gets an error that names only the approved directory: one that re-points a link in its `cwd` while Main decides, or puts another directory at that path, cannot move the command into a directory Main never saw, inside the roots or not. That check is by path, so the start itself is bound to the directory as well, and a Worker that renames the directory and puts a link at its path right after the check cannot move the command either. On Linux with `/proc` the daemon opens the directory, requires that descriptor to be the approved directory, and starts the command in `/proc/self/fd/<fd>`, its copy of the descriptor: the command runs in the approved directory, under whatever name it has by then. Elsewhere (macOS, and Linux without `/proc`) a descriptor cannot be a working directory, so the terminal starts as a short fixed script run by `/bin/dash`, with the directory, its device and inode, the command and its args as arguments: it changes into the directory, compares the one it is then in with that device and inode, and only then execs the command, which keeps the terminal's pid, process group, output and exit status. On macOS it runs outside the terminal sandbox and execs `sandbox-exec`, so the command is what is sandboxed, as before. On a mismatch nothing runs: the terminal exits with status 75 and the one line `Terminal cwd changed since it was approved: <cwd>` in its output. The script hands the terminal's `env` on to the command as it is, except that it sets `PWD` and `OLDPWD` and leaves out a variable whose name is not a shell name, such as an exported bash function (`BASH_FUNC_<name>%%`). It never runs under another shell: dash takes no code from the environment, while bash, the `/bin/sh` of macOS, Fedora and RHEL, would take functions and `SHELLOPTS`, and with them commands, from the Worker's environment, outside the sandbox on macOS. A host with neither `/proc` nor `/bin/dash` (a Linux without `/proc` that ships no dash, such as Fedora, RHEL or Alpine) starts the terminal by path right after the check above, as before, and so does Windows: there a Worker that swaps the directory between that check and the start can still move the command. Through the script, an unsandboxed command that cannot be found exits with status 127 and the shell's `not found` line instead of failing to spawn. Every terminal starts this way, auto-approved, on an approval or approved while it waited.
- Anything else, and a second run, is asked about anew with the full operation. Approvals end with the turn. Before 1.8.0 any approval let one write or terminal of the same kind through, whatever it was.
- A write or terminal waiting for Main counts its whole request as the Worker sent it, every field included whether it is used or not, against the session's pending-input byte budget, `maxPendingInboxBytesPerSession` (512 KiB). One that does not fit is refused with a JSON-RPC error to the Worker, and the bytes are released when it is answered or cancelled.

Claude sessions receive `_meta.claudeCode.options.disallowedTools` on `session/new` and on every restore. `read_only` adds `Bash`, `Edit`, `Write`, `MultiEdit` and `NotebookEdit`, and every policy adds path rules for the protected paths.

The Grok process is started with its cwd in a Gateway-owned directory (`ACP_GATEWAY_GROK_SANDBOX_DIR`, default `~/.cache/acp-gateway/grok-sandbox`) holding `.grok/sandbox.toml`, and with `GROK_SANDBOX=acp-gateway`:
- The profile extends Grok's `workspace` profile and denies every protected path to the whole process, through Seatbelt on macOS and Landlock on Linux.
- It covers Grok's in-process tools such as grep, which never reach ACP.
- Edits and terminals go through ACP and are unaffected by it; Grok's shell commands run in Gateway terminals, under the terminal sandbox above.
- Since 1.8.0 the profile is written as a new file in `.grok`, synced, and renamed over `sandbox.toml`. A `sandbox.toml` that is a link, symbolic or hard, is replaced, and the file it leads to is neither written nor emptied. Every directory on the way, from the filesystem root down to `.grok`, must be a real directory, created `0700` where missing; a symbolic link is followed only where no process of this user could have made it (root's, in a directory of root's that no one else may write unless it is sticky, such as `/var` on macOS, and never for a daemon that runs as root), and the sandbox directory and `.grok` must be this user's. Otherwise the profile is not written and Grok does not start, with an error naming the component. A Worker runs as the same user, so before, a `sandbox.toml` or `.grok` it turned into a link had the next Grok start write the profile into whatever the link led to, `install.json` included. On Linux, a directory swapped for a link between the check and the write can still take the new file, under the name `sandbox.toml` only.

`permission_policy_partial` carries `scope`, the list of things the engine cannot enforce for that provider and policy: `edit_inside_roots`, `shell_write_inside_roots`, `read_outside_roots`, `read_protected`.
- Codex under `read_only`/`ask` has all four; under `auto_approve` it has the two read scopes.
- Grok has `read_outside_roots`.
- A consumer should treat any capability absent from `scope` as enforced, and anything listed as possible.

## Snapshot workspaces

`session_open {workspace:"snapshot"}` copies `cwd` twice, before the worker starts: a working tree and an untouched baseline, as clonefile/reflink copies where supported. The diff is baseline → tree, so later edits to the original never show up as reversed worker edits. A symlink inside the tree is re-pointed into the copy; one leaving the tree is not copied and is listed in `workspace.droppedLinks`. Protected directories are never copied, and a protected `cwd` is refused. The diff is capped at 64 MiB, beyond which it fails with `WORKSPACE_ERROR`. The copy lives under `ACP_GATEWAY_WORKSPACES`, default `~/.cache/acp-gateway/workspaces`, never under a protected path. The session's `cwd` is the copy, and the response carries `workspace:{mode,source,path}`. Direct sessions have no `workspace` key.

Symlinks are copied as links, and sockets/FIFOs are skipped. The copy is limited to 1 GiB and 200,000 entries; beyond that, or when `cwd` contains the workspace root, the open fails with `WORKSPACE_ERROR`. `additionalDirectories` are not copied. Since 1.8.0 all live copies together are also limited to 4 GiB, counted in the same measured source bytes as the per-copy limit (each copy is stored twice, as tree and baseline). Copies of open sessions, copies still being opened and deleted sessions' copies that are not gone yet all count. An open that would go past it fails with `WORKSPACE_ERROR` and `details: {bytes, usedBytes, limitBytes}` before anything is copied.

`session {action:"workspace_diff", sessionId}` returns `{changed, files, patch, patchBytes, truncated, patchArtifact?}`. `patch` is a `git diff --no-index` patch from the original (a/) to the copy (b/), with tree-relative paths, applicable with `git apply` in the original. It is capped at `maxInlineResultBytes`, with the complete patch as an artifact.

The engine never applies the patch. The copy is deleted on close and by session retention. It survives daemon restarts. A delete that fails is kept and retried by every maintenance pass, instead of being forgotten with the session record. Each copy holds an `owner.json` (beside `tree` and `base`, outside the worker's cwd) naming the Gateway state that made it. At startup and on every maintenance pass the engine deletes `ws-*` copies under the workspace root that carry its own marker and that no session references, such as a copy left by a crash between copying and registration. Copies without a marker or with another state's are never deleted, because daemons with separate state can share the default workspace root. A copy made before 1.8.0 is marked when a session that still references it is loaded.

## Caller identity

Since 1.6.0 a control request may carry `caller: {provider, sessionId, pid, instanceId}`. The control MCP server fills it once at startup from the agent CLI that spawned it: `provider` from the parent process name (`claude`, `codex`, `grok`, else `null`), `sessionId` from that CLI's exported id (`CLAUDE_CODE_SESSION_ID`, `GROK_SESSION_ID`, `CODEX_THREAD_ID`; Codex exports none to MCP servers, so `null`), `pid` of the parent, and a random `instanceId` per server process. Every Main on a machine shares one `rootId`; `caller` is what tells them apart.

- `openedBy` is the caller of the `session_open` or first `session_restore` that registered the session. Since 1.8.0 only an adoption rewrites it (see Per-Main isolation), keeping the previous value as `adoptedFrom`.
- `promptedBy` is the caller of the latest `prompt`, `run` or `task_prompt`. The same value is on that turn's `turn_start` event, so each turn names the Main its reply is for.
- Both appear on session responses, `session list`, and survive restarts. They are absent when the caller sent nothing (pre-1.6.0 control servers), so the old shapes are unchanged.
- Only `control` connections are recorded. An `observer`'s `caller` is not recorded; its `pid` still counts for the Worker check below. A malformed `caller` drops attribution, never the call.
- `sessionId` can go stale when the CLI switches sessions (for example Claude `/clear`) while the MCP server keeps running; `pid` and `instanceId` stay valid.

### Per-Main isolation

Since 1.8.0 the Gateway enforces what `caller` tells apart. A control request that carries a `caller` comes from a front-door Main and reaches only:
- sessions whose `openedBy` is that caller, by the `scope:"mine"` rule below (session ids decide when both sides have one, else `instanceId`);
- the tasks and inbox rows of those sessions. A task follows its session while the session record exists, then the Main that adopted the session (see below), else its own `caller`, because a handle outlives its session. An inbox row keeps its session's owner after the session is closed;
- records no Main is recorded for: sessions opened before 1.6.0 or by a client that sends no `caller`, with their tasks and inbox rows. Every Main shares these, as before.

Another Main's record answers as another root's does:
- `NOT_SESSION_OWNER` for every call that names its session: `session` get, check, workspace_diff, close, pin and unpin, `config`, `poll`, `prompt`, `run`, `task_prompt`, `task_run`, `permission`, `answer`, `cancel`, and a `session_restore` that would reuse its record (unless the adopt rule below hands the record over);
- `NOT_TASK_OWNER` for `task_get`, `task_result`, `task_cancel` and a `run` attach (`{taskId}`), and `NOT_INBOX_OWNER` for `inbox get`;
- a link to its task is an unknown id (`INVALID_ARGUMENT`), and `ack` skips its task as `not_task_owner`;
- a task the caller can read (one on a shared session) never names it: its id is left out of that task's `parentTaskId` and `inputTaskIds`, and a key with nothing left is absent. A link to a task that no longer exists stays readable only to the Main that declared it.

Lists leave such records out and keep their shapes (an argument-free `task_list` stays unpaged): `session list`, `task_list`, `inbox list` and `attention`, setup's `sessions_stall_suspected` and attention alerts, and `subscribe` without `sessionIds`, which also never streams a session another Main opens later. `subscribe` with `sessionIds` needs every id to be reachable. `session clean` closes only the caller's own sessions, never the shared ones. It names no session: a `sessionId` sent with it changes nothing, another Main's included (before 1.8.0 `clean` failed without one).

Requests without a `caller` keep root-wide access, unchanged. These are management requests (AgenLynk and other public-client consumers, `acp-gateway-admin`, installer health checks) and pre-1.6.0 front doors. Every observer keeps it too. `setup`, `gateway_config`, `provider`, `retention_preview`, `shutdown_if_idle` and `daemon_shutdown` stay root-level for everyone.

A Main is its CLI session. A front door restarted in the same CLI session (a new `instanceId`, the same `sessionId`) keeps its sessions. Each Codex thread is a Main of its own; a Codex front door that sends no thread id is one Main per process. A Main that comes back under another identity is another Main, for example a new CLI session, or a restarted front door that sends no session id (Auggie, Claude Code without `CLAUDE_CODE_SESSION_ID`, Codex calls without thread metadata). It takes its earlier sessions back by the adopt rule:
- Only `session_restore` adopts, and only a call that names an open record of its root exactly: `provider`, `acpSessionId` and the record's `cwd` (for a snapshot session, its copy or the directory it was copied from). `session list` and `get`, `poll`, `subscribe` and every other call keep answering as above.
- Only once the Main that holds the record is gone: no live control connection that sent its `caller` (a connection speaks for every `caller` it sent until it closes) and no live subscription of its. Root presence does not count, since every Main shares the root. While that Main is present, and for a `cwd` that does not match, the restore answers `NOT_SESSION_OWNER` and says nothing more. A daemon restart drops every connection, so a Main whose front door has not called (or resubscribed) since then counts as gone.
- A record no Main is recorded for is never adopted: it stays shared, and restoring it changes nothing about who may reach it.
- Adopting moves `openedBy` to the caller and keeps the previous one as `adoptedFrom`, which session responses carry wherever they carry `openedBy`, except polls. The record's tasks and inbox rows go with it, also once the session is closed, and its finished tasks become the caller's to receive: `attention` lists the unseen ones, collecting one marks it seen, and `ack` takes them. Each task keeps its `caller`.
- The restore then goes on as the owner's own would: a worker that is still connected answers `INVALID_ARGUMENT` (already registered, with `details.sessionId`), a busy session `SESSION_ACTIVE`, and otherwise the worker is restored.
- Repeating the restore changes nothing. An adoption is written with the next state snapshot (within about a second), not to the write-ahead log, so a Gateway crash in that window can hand the record back to its previous owner; the same restore takes it again. Closing an adopted session, by `session close` or by session retention, saves the adoption first: when the snapshot may not hold it yet, the snapshot is written and synced before the close is logged, so a crash after the close cannot hand the session's tasks and inbox rows back to the previous owner with no session left to restore. Without the write-ahead log the close and the adoption reach the same snapshot.
- When that synced write fails (for example the state directory stops taking new files while the open log still takes appends), the close is not logged and the record is not removed. `session close` still answers as a close (`{ok:true, closed}`), ends the worker session and deletes a snapshot copy as always, and the record stays, `status:"closed"`, until the adoption can be saved; persistence health says why (`setup` `persistence.healthy:false` and `error`). Such a record reads as closed (`get`, `list`, and `check` with the `session_closed` caveat) and is never worked on again: `prompt`, `run`, `task_prompt`, `config`, `permission`, `answer`, `pin`, `unpin` and `workspace_diff` answer `SESSION_CLOSED`, and nothing reaches a worker. Every maintenance pass, and another `close` or `clean` that reaches it, tries the save again, then removes the record and logs its close; that `close` answers as a close, and `clean` does not list the record as closed again. Its tasks and inbox rows stay the adopter's throughout. A crash before then brings the record back as the last snapshot holds it: open and still the previous owner's when no snapshot holds the adoption yet, for the same restore to take again with its tasks and inbox rows, or closed and adopted when one does, and then the first maintenance after the restart removes it.

Management clients reach every record already and never adopt. An embedded `GatewayService` (no daemon) cannot tell whether a Main is gone, so it treats every owner as present and adopts nothing unless it is given `isOwnerLive`.

Like observer access, this is not a credential boundary: a process that holds the token can send any `caller`, or none. It keeps Mains that share a machine from reading, answering for, steering or cleaning up each other's work.

## Workers never get the Control

A Worker's own agent CLI can load the user's MCP configuration (Codex reads `~/.codex/config.toml` for the Workers the Gateway starts) and with it the Control MCP. Since 1.8.0 three checks keep the Control from a Worker:

- The Gateway sets `ACP_GATEWAY_WORKER=1` on every process it starts for a Worker: the provider process and each terminal it opens. A Worker cannot remove it from a terminal's env.
- The Control MCP server refuses to start inside a Worker's process tree: when that variable is set, or when an ancestor process is the daemon (its command line runs `gateway-daemon.js`, or it holds the daemon lock `<socket>.lock`). A daemon that died can leave its lock behind, naming a pid another process has since taken, so the lock's pid counts only when its command line runs the daemon, or cannot be read while the server cannot read its own process entry either. The daemon runs as the same user, whose processes `hidepid` (below) never hides, so a lock pid the server cannot read while it can read itself is another user's process or gone, not the daemon: a stale lock's pid taken by a root-owned process above a Main, such as the `sshd` of its SSH login, no longer refuses that Main. When a process the server cannot read cuts its walk up the ancestry short, the walk ends there, as no daemon above, as long as the server can read its own process entry: with `/proc` mounted `hidepid=1` or `2` a user cannot see another user's processes, so a Main started over SSH stops at the root-owned `sshd` above its login shell. That loses nothing, because the daemon runs as the same user: the chain from a Worker's CLI up to the daemon is that user's own processes, which `hidepid` never hides. Only where the server cannot read even its own entry, on a macOS or Linux host with no `/proc` and `ps` missing or blocked, does it refuse for that: it could not tell a Worker from a Main there, and a Worker could hide the daemon above it by blocking the lookup. Its stderr line then says that it cannot tell whether it runs inside a Gateway worker, not that it does. A refused server exits with status 77 and a one-line reason on stderr, before it reads the identity or touches the socket. A Main's own server is never under the daemon, which is a detached child of the front door that started it.
- The daemon refuses a request whose `caller.pid` is, or runs under, the daemon or a process the daemon spawned for a Worker — a provider or one of its terminals — with `WORKER_CONTROL_DENIED`, before the connection binds or anything runs, `daemon_shutdown` included. It walks the caller's ancestry once, matching both the daemon's own pid and the live pids of the processes it spawned. The lookup happens on the first request that names a pid, and the verdict is reused only while the connection's `caller.pid` stays the same; a request that names a different pid is checked on its own. A connection that never names a `caller.pid` (management clients: AgenLynk, the admin CLI, installer health checks) is never refused for this. A spawned pid is in the set from the spawn until its process exits, whatever the Gateway has done with the process meanwhile: a start that failed, an adapter update that retired it, a transport failure after which a new process took its place, or ending it with SIGTERM and then SIGKILL after the grace. It leaves the set the moment the process exits, so a later process that reuses the number is not refused. A walk that places the caller under none of them does not prove it is a Main, because the caller's pid, which the daemon does not control, may simply be gone; so the daemon then reads its own process entry, which it knows is alive. If that read fails too, the host cannot read ancestry at all (no `/proc`, and `ps` missing or blocked), no caller can be placed, and the request is refused with `WORKER_CONTROL_DENIED` and the message `Control access denied: caller process <pid> ancestry cannot be verified on this host`; if it succeeds, the caller runs outside and is served. On Windows, which has neither `/proc` nor `ps`, an ancestry that cannot be read is refused at neither end, so there a Worker is told apart only by the `ACP_GATEWAY_WORKER` variable, or by a pid that is itself the daemon's or one the daemon spawned. The daemon-pid match cannot count pid 1, which ends every chain, so when the daemon is pid 1 (a container entrypoint with no init) it cannot tell a Worker apart by the daemon's own pid; the spawned-process match still does, because a provider or terminal pid is a real child the caller descends from and never pid 1, and the `ACP_GATEWAY_WORKER` variable remains a backup.

`session_open` and `session_restore` refuse, with `INVALID_ARGUMENT`, a Worker `mcpServers` entry named `agent-acp` or `agent-acp-control`, or that mentions `acp-gateway-control`, `acp-mcp-bridge`, `gateway-daemon` or `control-mcp`; one whose env sets `ACP_GATEWAY_CONTROL_TOKEN`, `ACP_GATEWAY_ROOT_ID` or `ACP_GATEWAY_INSTALL_STATE` (ACP's `[{name,value}]` or an object); one whose command or arguments run a Control bin (`acp-gateway`, `acp-gateway-control`, `acp-mcp-bridge`), as a bare word (the command, or an argument as in `npx acp-gateway`) or a file of that name, or a file that resolves to a Gateway's `src/index.js`, such as `~/.acp-gateway/runtime/current/gateway/src/index.js`. In the command and arguments, a path the Gateway can look at (absolute, or under `~`) counts by what is there: a directory never counts, whatever its name, so a filesystem server may be rooted at a checkout called `acp-gateway` or `acp-mcp-bridge`; a file counts by its own name and what it resolves to, not by the directories it sits in. A path the Gateway cannot look at, one that is not there or a relative one (it resolves against the server's working directory, which the Gateway does not know), names a bin only as the command, which is never a directory; a relative path still counts whole as a mention. So as an argument `../acp-gateway` names no bin, while `../acp-mcp-bridge` still mentions one.

Like observer access, this is not a credential boundary: a process that holds the token and can start processes outside the daemon's tree is not stopped by it.

## Task links and scope

- `run`, `task_prompt` and `task_run` accept `parentTaskId` (the task this one follows up) and `inputTaskIds` (1 to 16 unique ids of tasks whose results went into the prompt). Every id must name a task the caller can see: on its root and, since 1.8.0 for a front-door Main, its own or one no Main is recorded for (see Per-Main isolation). Otherwise `INVALID_ARGUMENT` with `details.unknownTaskIds`, and nothing starts. The Gateway records them as declared and never infers links. `prompt` creates no task, so it refuses them, as does a `run` attach (`{taskId}`).
- Task reads carry `parentTaskId`/`inputTaskIds` only when declared. They survive restarts. Since 1.8.0 a front-door Main's reads leave out a link to a task it cannot see (see Per-Main isolation).
- `task_list` filters `parentTaskId`, `callerSessionId`, `callerInstanceId` combine with `status` and paging. Any of them selects the paged response.
- `scope:"mine"` on `session list` and `task_list` keeps records whose `openedBy`/`caller` is the requester: session ids decide when both sides have one, else `instanceId`. Records with no caller are nobody's. A Codex front door that sends no thread id matches by `instanceId`, so its threads are one Main. A request without a caller (observer, pre-1.6.0 front door) gets `INVALID_ARGUMENT`. Without `scope`, a front-door Main's lists hold its own records plus those no Main is recorded for (since 1.8.0), and management and observer lists hold the whole root.

## Idempotency and worker errors

A `run` whose `idempotencyKey` already names a run on the same session attaches only when the prompt, model and declared links digest match (input order aside). Otherwise it fails with `IDEMPOTENCY_CONFLICT`, and `details.taskId` holds the existing task. Changing `waitMs` or `resultBudgetBytes` on a retry is not a conflict. Runs recorded before 1.5.2 carry no digest and keep the old attach behavior.

A JSON-RPC error from the worker becomes `ACP_ERROR`, or `UNKNOWN_SESSION` for a `session/load|resume` of a session the worker does not know. The message keeps the historical `ACP error <code>: <message>` text, and `details.{method,acpCode,acpMessage,acpData?}` preserve the original.

## Worker requests and frames

Since 1.8.0:
- A worker request's id stays the JSON type the worker chose, a string or an integer. Events, inbox rows, `permission_response` and `elicitation_response` carry it exactly, and `permission` and `answer` take `requestId` as either type (`INVALID_ARGUMENT` for anything else). An id Main sends as the other type's spelling, `"7"` for request `7`, still answers the one pending request it spells. Before, the Gateway read `requestId` as a number, so a request with a string id could not be answered.
- A permission request or question that the session's command queue cannot take at that moment (32 commands, plus 2 kept for the worker's requests) is answered at once with a JSON-RPC error (`-32000`, `Session <id> has too many queued commands`), and no inbox row is made for it. Before, it was dropped there while the worker went on waiting for an answer, with nothing for Main to answer. A turn's end and the provider's exit are queued whatever the depth.
- A line from a provider that is JSON but not a message the Gateway can act on (not an object, an `id` that is neither a string nor a number, a `method` that is not a string, or `params` that are not an object) is dropped; the first 16 per provider process are noted in its stderr tail, which a provider setup failure reports, and the rest only counted. One that is still a request with a usable `id` is answered with a JSON-RPC error, `-32600` for the method and `-32602` for the params. A line that is not JSON is ignored, as before. None of this ends the provider, and no line a provider writes ends the daemon; before, a single `null`, a numeric `method` or `null` `params` ended the daemon and every Main's sessions with it.
- A request under an id the worker already has a request pending under, one the Gateway is still handling or one waiting for Main (a write or terminal waiting for approval included), or under the id that reads the same in the other JSON type (`"7"` while `7` is pending), is answered `-32600` (`Invalid Request: id is in use by a pending request`) and noted like a dropped frame; the pending request keeps the id, and Main's answer goes to it. Before, a terminal or write under the id of a permission request Main was shown took its place, so Main's approval of what it saw ran the other operation, and a permission request under the id of a pending terminal waited for good.
- A permission request or question for a session the provider process does not serve, one never opened on it or already closed or unloaded, is answered at once with `-32000` (`Unknown ACP session: <id>`) instead of being kept, and so is one past 1024 waiting for Main across all the sessions of one provider process, writes and terminals waiting for approval included (`ACP provider pending request limit exceeded: 1024`), on top of the 64 per session. A session the Gateway clears (closed, unloaded, or a restore that failed) now also answers the permission requests still waiting there, as cancelled, as it already answered its questions and its writes and terminals waiting for approval. Before, such a request was kept with no Main to answer it, the worker waited for good, and since the session id is the worker's to choose, nothing bounded how many were kept.
- `cancel` never overtakes its own prompt. A prompt still waiting in the Gateway's queue for a provider that is not reading its input is taken back: it never reaches the worker, the turn ends `cancelled`, and the worker is sent no `session/cancel` for it. A prompt already sent is followed by its `session/cancel`. Before, the cancel went out first, found no turn to stop, and the prompt then ran the turn Main had cancelled, recorded as cancelled.

## Adapter generations

A process is reused only while its provider definition (command, args including the adapter pin, env) is unchanged. After an adapter update, the old process keeps serving the sessions it holds, new sessions start a process of the current definition, and maintenance stops the old one when it serves nothing. Summary and full `setup` report `started` from real process liveness. `setup {provider}` adds `runningVersion` and `retiredProcesses`.

When `ACP_GATEWAY_STATE` points outside `~/.acp-gateway` and `ACP_GATEWAY_PROVIDERS` is unset, provider definitions and the registry cache live next to that state file. Reads fall back to the global definitions until the first write, which copies them.

## Retention preview

`retention_preview {values:{sessionRetentionMs,taskRetentionMs,inboxRetentionMs,resultRetentionMs}}` accepts any subset of those keys; direct top-level names are also supported. No deletion occurs. Unsupported policies such as artifactSessionLimit are rejected.

Response: `{ok,advisory:true,scope:"root",calculatedAt,configRevision,values,counts:{sessions,tasks,inbox,results},artifacts:{exact:false,reason}}`. Counts use the same predicates as GC and describe the records of the caller's root, every Main's included (retention is root-level), at the supplied policy. Active work and pending input are protected; pinned records are excluded from age retention while their session is open (since 1.8.0 a closed pinned session, and the records hanging off it, age out like any other). Task TTL is a separate, explicit handle lifetime and can still expire independently of pinning.

Preview is advisory: time, new work, references and settings can change before a restart/GC. Do not show it as an immutable deletion plan or a count covering other roots. Artifact reference protection prevents an exact byte/count forecast from age alone. Consumers should not invent artifact counts. In the normal single-user daemon, one root owns the engine's work.

## Replay and result integrity

`subscribe` returns the existing sessions/events/cursorTruncated fields and `replay`, keyed by session ID: `{complete,retainedTruncated,liveOnlyMissing,fromCursor,nextCursor}`. Message/thought chunks remain live-only; retained control/tool events remain bounded. A missing relevant raw chunk now also sets cursorTruncated, so older consumers cannot call that replay complete. Poll remains a retained-result/control view and does not treat intentional absence of raw chunks as poll history loss.

The replay is one reply, so since 1.8.0 it is bounded by bytes: half of `maxQueueBytes` (2MB by default) of serialized events across all sessions it covers. It is filled newest first, one event per session in turn, so one busy session cannot crowd out the others, and each session keeps an unbroken run of its newest events. A session whose older events did not fit reports it the way any incomplete replay does (`cursorTruncated` true, `complete` false), plus `budgetTruncated: true`, `omittedEvents` (how many matching events were left out) and `omittedBefore` (the first replayed sequence). Those events are still retained: `poll` with `cursor` set to `fromCursor` and `toCursor` set to `omittedBefore` reads them. A replay that fits has the same shape as before.

On client reconnect, `subscription_replay_truncated` still notifies callbacks of incomplete history. A gap/reconnect and healthy transport must never imply complete history. After daemon restart, the prior non-persisted event history is explicitly marked truncated. Fetch completed tasks through task_list/task_result and follow bounded artifact pointers for results; do not resubmit prompts to reconstruct a timeline. No persistent raw transcript journal is advertised.

Since 1.8.0 `GatewayRpcClient` restores each subscription on its own: one whose resubscribe the daemon refuses, because a session it names is gone or no longer this Main's, or that gets no answer in time, ends with a `subscription_error` event (`error`, and `errorCode` when the daemon gave one), as a subscription the daemon drops does, and the others are restored. Before, the first refusal left every later subscription without events, on a connection that looked healthy, and no reconnect restored them. A `close()` while a connection is still being made ends it too: the attempt connects nothing and sends nothing, any socket it opened is destroyed, and the calls waiting on it reject with `Gateway client is closed`. Before, the attempt went on to connect after the close and sent the call.

At most 64 subscriptions per root. Invalid cursors fail before registration. Aborting a run wait releases its waiter immediately and leaves the worker running. Since 1.8.0 a long `poll` does the same: when its request is cancelled or its connection closes, the wait ends at once with `WAIT_ABORTED` and no response is built, so a result it would have carried is not counted as delivered. Only explicit task/session cancellation cancels the worker.

## Runtime identity and invariants

Full setup adds `runtimeRoot`, `gatewayBuildId`, `instanceId`, `sourceCommit`, `configRevision`, and `capabilities`. Build ID hashes the actual src JS file names/bytes at process start, cached for that process. It is not the archive digest or builder commit. Compare like identities; use instanceId to distinguish restarts. sourceCommit is taken from release manifest and null in a source checkout.

Required invariants and validation:

| Invariant | Gate |
|---|---|
| Work has a durable Task handle before ACP dispatch | crash matrix task-create barriers |
| Completed Task results survive restart or explicitly fail durability | result commit/artifact/fsync crash matrix |
| Unknown execution outcomes are not silently retried | restart recovery + idempotency tests |
| Observer cannot mutate or keep an owner alive | engine management + daemon RPC tests |
| Disabled provider cannot start a new registered session | actual public-client tests, including daemon restart |
| Shutdown cannot race a newly admitted open | engine admission race tests |
| Aborted readers free their budget without cancelling work | TaskStore/run cancellation tests |
| GC cannot remove active obligations or referenced artifacts | retention/resource/persistence tests |
| Unrecoverable event history is explicit | replay completeness tests |

Release builders require a v1.5.x tag (v1.5.0 through v1.5.2), v1.6.0, v1.7.0, v1.7.1, v1.7.2 or v1.8.0 plus an independently supplied reviewed source SHA; verifiers require the same SHA. Existing v1.4.0's historical pin is retained. New archives use the public client and engine from the same source commit. Checksums and local unsigned build records are not signed provenance; the separate release workflow attests and verifies before publishing without overwriting assets.
