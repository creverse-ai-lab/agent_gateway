# Gateway 1.5.x management contract

ACP Gateway is the engine. AgenLynk and other consumers render and invoke this contract; they must not independently implement execution, retention, provider or permission policy. API major remains 1 and state schema remains 5. New capability discovery is on **full** `setup`, leaving summary payload costs unchanged.

## Public boundary

Import `GatewayRpcClient`, `GatewayError`, `ERROR_CODES`, `GATEWAY_API_VERSION` from `acp-gateway-daemon/client` (the npm package and a source checkout). A runtime release that an app installs and mounts keeps the package name `acp-gateway`, so there the same four exports come from `acp-gateway/client`. No private engine imports are needed. `client.call(method, arguments, timeoutMs, {signal})` returns the RPC result or throws an error with stable `code` and optional `details`. A failed call is never evidence that an already-started worker did not execute; use the Task handle and idempotency key to reconcile.

`GatewayRpcClient({token, rootId, access: "control"|"observer", autoStart})` defaults to control for old consumers. Role is bound on the first authenticated request and cannot change on that connection. Observer uses the existing token, so this is server-enforced read-only behavior, **not** a separate credential boundary against an actor that possesses the control token.

Control socket: `ACP_GATEWAY_SOCKET`, else `acp-gateway-<uid>.sock` in the OS temporary directory, which is per user on macOS and usually the shared `/tmp` on Linux. The daemon binds it under umask 177, so it is created 0600 and never reachable by another user, not even for an instant. Since 1.8.0 the client checks, before it connects and again once connected, that the path holds a socket owned by the current user, and before it connects it also checks that the socket's whole directory chain — every component from the filesystem root down to the directory holding it — is owned by the current user or root and writable by no one else, unless a directory is sticky (a world-writable `/tmp` lets only an entry's own owner replace it). An `lstat` of the socket alone rejects a final symlink but follows an intermediate one, so a parent directory a stranger can replace with a link could point the connect at a foreign socket while both owner checks still saw the real one; a chain no other user can write is one no other user can redirect, which is what stands in for reading the connected peer's uid (there is no `LOCAL_PEERCRED`/`SO_PEERCRED` in Node without a native addon, which the Gateway does not ship). Otherwise the call fails with `SOCKET_UNTRUSTED` — `details: {socketPath, type, ownerUid, uid}` for the socket itself, `{socketPath, dir, …}` for an untrusted directory in the chain — before anything is written, the token included, and no daemon is started; `daemon_shutdown` and `shutdown_if_idle` report it too instead of `alreadyStopped`. The daemon makes the same directory-chain check before it touches anything at the path — its lock file, the probe and removal of a stale socket, the bind — and, rather than put its socket where another user could swap a link for it, refuses to start: it records `SOCKET_UNTRUSTED` in the recovery marker and exits with status 78. The client and the daemon check one path only, the canonical one: each resolves the socket's directory as the kernel does, links and `..` included, and uses the socket's name in that real directory for the check, the connect and the bind alike, never the path as written, whose links the kernel would resolve again at each use, after whoever owns one could have pointed it elsewhere. The default paths pass (a per-user temporary directory on macOS, a sticky `/tmp` on Linux); a hand-set `ACP_GATEWAY_SOCKET` in a directory group- or other-writable and not sticky is what this turns away. On Linux another user can still create the default path first and so keep the Gateway from starting; set `ACP_GATEWAY_SOCKET` to a path in a directory only you can write, such as `$XDG_RUNTIME_DIR/acp-gateway.sock`, for every client: the Control MCP entry, apps, `acp-gateway-admin` and the installer. Where there is no uid to compare (Windows) the check is skipped.

Control identity: the installer keeps the token and root id in `install.json` `identity.{token,rootId}` (`ACP_GATEWAY_INSTALL_STATE`, default `~/.acp-gateway/install.json`, mode 0600), and nowhere else. Since 1.8.0 the Control MCP entry it registers in an agent CLI carries neither, only `ACP_GATEWAY_INSTALL_STATE` when the file is not at its default path. The front door, like a consumer, takes each once, when it starts, from its environment (`ACP_GATEWAY_CONTROL_TOKEN`, `ACP_GATEWAY_ROOT_ID`) when set, else from that file; a token in neither is an error, a root id in neither falls back to `main-<ppid>` as before. A client that autostarts the daemon hands it the identity it holds (its own, else the one in its environment) as one JSON line on the daemon's stdin, and sets only `ACP_GATEWAY_IDENTITY_STDIN=1` in the daemon's environment: the OS keeps a process's initial environment readable by any process of the same user (`ps -E` on macOS, `/proc/<pid>/environ` on Linux), and the daemon's pid is in `<socket>.lock`. On Windows the identity still goes in the environment. A daemon started with `ACP_GATEWAY_CONTROL_TOKEN` set (by hand, by a supervisor, or by a consumer that launches it itself) takes the identity from there and never reads stdin, and then the token stays readable in that process's environment block. A daemon told to read stdin that gets no usable line there (none within 5 seconds, more than 16 KiB without a line end, or no token of at least 24 characters) exits with status 78 and records `DAEMON_IDENTITY_INVALID` in the recovery marker file, which the client reports. Either way the daemon removes the identity from its own environment, so no process it starts (Workers, terminals, adapter updates through npm or uv) inherits it, nor `ACP_GATEWAY_SOCKET` or a Main's session markers. Everything else in the daemon's environment, which comes from whatever started it (a client's autostart, a supervisor, a consumer), still reaches Workers and their terminals, API keys, cloud credentials and `SSH_AUTH_SOCK` included, so a provider that signs in through its environment keeps working; there is no allowlist. `acp-gateway-bootstrap --rotate-token` replaces the identity in the file only: a consumer that cached it must read it again, and a running daemon accepts only the identity it started with until it restarts.

Observer calls: setup without provider/refresh; session list/get; config list without worker restore; poll; task_get/list/result; inbox list/get/attention; subscribe/unsubscribe; gateway_config get; provider list; retention_preview. All other calls fail with `OBSERVER_ACCESS_DENIED`. Observer traffic never attaches owner presence or touches owner activity. Credentials are still required for every method except public guide.

## Engine settings

`gateway_config {action:"get"}` (default action) returns:

```json
{
  "ok": true,
  "revision": 0,
  "activeRevision": 0,
  "pendingRestart": false,
  "pendingLiveApply": false,
  "unsupportedLegacySettings": [],
  "options": [
    {
      "id": "idleUnloadMs", "group": "lifecycle", "type": "number",
      "environment": "ACP_GATEWAY_IDLE_UNLOAD_MS", "minimum": 0,
      "defaultValue": 1800000, "currentValue": 1800000,
      "configuredValue": 1800000, "storedValue": null,
      "source": "default", "editable": true,
      "requiresRestart": true, "pending": false
    }
  ]
}
```

The example shows one option; get returns the complete supported catalog. Number values are safe integers. Booleans are JSON booleans and enum options declare `values`. Unknown settings are rejected; arbitrary provider env, commands, secrets and recovery overrides are not exposed as writable settings.

`gateway_config {action:"set", expectedRevision:N, values:{...}}` stages settings. `gateway_config {action:"reset", expectedRevision:N, ids:[...]}` resets selected keys to defaults. Revision mismatch or ENV-locked keys fail with `CONFIG_CONFLICT`. Invalid values/cross-field budgets fail with `CONFIG_INVALID`; unsupported keys use `INVALID_ARGUMENT`. All settings currently require restart, including adapter update policy. Saving is not applying.

Precedence: environment > engine settings file > defaults. If the engine settings file does not yet exist, supported values from legacy `install.json.gatewayConfig` and `agentUpdates` substitute for stored values. The first successful write materializes them into settings.json without rewriting install identity, managed MCP, skill or UI settings. Unsupported legacy engine keys are reported. Once migrated, legacy changes are not imported again. CLI installer update-policy flags write through the same settings store.

Paths: `ACP_GATEWAY_SETTINGS` overrides the engine settings path. Otherwise it is `settings.json` next to `ACP_GATEWAY_INSTALL_STATE` (default `~/.acp-gateway/install.json`). Use explicit paths for isolated deployments. Writes use exclusive locks, fsynced private temporary files, rename and parent-directory fsync. A `CONFIG_BUSY` lock after a crash requires inspecting its recorded PID and confirming no writer exists before removing only that `.write.lock` file. The engine does not silently steal stale-looking locks.

## Providers

- `provider {action:"list"}` returns `{ok,providers}` including boolean `enabled` and installed adapter metadata.
- `provider {action:"set_enabled",provider:"claude",enabled:false}` persists engine policy and returns `{ok,provider,enabled}`. Off blocks **new registrations**, including external session_restore, before starting work and again at registration. Already registered sessions can continue and reconnect. Policy is read per admission, independent of cached worker clients.
- `provider {action:"install",registryId:"claude-acp",dryRun:true}` uses the official Gateway installer. Dry-run is the default; only explicit `dryRun:false` installs. The result is the installer action/warning envelope. Set an adequate RPC timeout for installation. Request cancellation cannot undo an external package-manager operation that already started. Enabling/disabling is a separate operation; installation preserves the current disabled list.

Consumer-owned npm/uv invocations or copies of provider resolver policy are unnecessary. Distribution verification and provider definitions remain in the engine's installer/registry implementation.

## Safe shutdown and applying settings

`shutdown_if_idle {}` rejects with `SHUTDOWN_BLOCKED`, `details.blockers` when active sessions, tasks, unanswered inbox records, pending session admissions, in-flight mutations, provider starts, maintenance or agent updates exist. A successful admission atomically closes mutation admission before acknowledging shutdown. Further mutations fail with `GATEWAY_DRAINING`. A blocked attempt restores admission.

`daemon_shutdown {}` now uses the same safe default. Since 1.5.2 the public client never autostarts a daemon for `daemon_shutdown` or `shutdown_if_idle`; with nothing listening it returns `{ok:true, alreadyStopped:true}`. `daemon_shutdown {force:true}` is an explicit destructive override for trusted control clients. OS SIGTERM/SIGINT remain unconditional shutdown. Force can interrupt workers; it does not claim their external side effects were rolled back.

Since 1.8.0, whenever the Gateway ends a provider process (a shutdown, an idle unload, maintenance stopping a retired adapter generation, or a fatal transport error: a line from the provider over the frame limit, or a provider that stops reading its stdin), it sends SIGTERM, then SIGKILL if the process is still running 2 seconds later, and stops waiting 2 seconds after that. The terminals the provider opened are ended by process group, with the same SIGKILL fallback. Before, a provider got only the SIGTERM, so one that ignored it kept running.

Consumer restart sequence: close automatic subscription clients; request safe shutdown; wait for old process/socket/lock to exit; select/start the intended runtime; reconnect and verify build identity and active settings. A successful shutdown is not itself a new runtime activation, and saving config does not restart either application or engine. Legacy 1.4 daemons do not enforce this new safe shutdown contract; require capability before presenting it as safe.

## Permission policy enforcement

`permissionPolicy` is enforced on what reaches the Gateway over ACP: file and terminal callbacks and `session/request_permission`. A worker that edits through its own tools without asking bypasses it. For `read_only` and `ask` sessions, the engine selects the worker's advertised `mode` value `read-only` on open and on every restore. When a provider is known to still edit inside its session roots without a request (Codex), `session_open`/restore put a `{level:"warning", code:"permission_policy_partial", provider}` alert first in `relevantAlerts`. Consumers must show it and must not present such a session as edit-proof. The alert is additive; its absence does not certify complete enforcement for other providers.

Since 1.5.2, automatic decisions also depend on paths:
- The engine compares every path a request names (`toolCall.locations[].path`, and `file_path`/`path`/`notebook_path` in `rawInput`) with the session roots, resolving symlinks.
- A path outside the roots is never auto-approved. `read_only` refuses it. `auto_approve` sends it to Main as a normal pending permission request.
- Gateway-protected paths are refused under every policy, including `ask`, and are never shown to a human. They are `~/.acp-gateway`, the install/settings/state directories, and the control socket. `fs/read_text_file`/`fs/write_text_file` refuse them even inside a root.
- Since 1.8.0 `fs/read_text_file` and `fs/write_text_file` open the file once and read or write only through that descriptor. The open refuses a symbolic link as the last component (on macOS anywhere in the path) and anything but a regular file, such as a FIFO or a directory. After it, the path must still resolve to the checked location and to the opened file; on Linux the descriptor's own path (`/proc/self/fd/<fd>`) is compared as well, and a lookup there that fails for any reason but a missing `/proc` (a `/proc` mounted but unreadable, or a path longer than `PATH_MAX`, which a Worker can produce with a link to a deeply nested directory) refuses the read or write. Only a host without `/proc` goes without that comparison. A Worker that renames or symlinks inside its roots therefore cannot redirect the operation between the check and the open, and a write empties the file only after that check. Every check so far is about names, and a hard link is a second name for the same file: link(2) needs no read permission on its target, so a Worker can give a protected file a name inside its roots (`ln ~/.acp-gateway/install.json ./notes`). So the opened descriptor is also compared, by device and inode, with every regular file directly inside a protected directory (the token in `install.json`, and the engine settings and state kept beside it), and a match is refused, for reads and writes alike, before a byte is read or the file is emptied. A protected path or a file directly inside one that the Gateway cannot stat, or a protected directory it cannot list (a mode or an I/O error hiding them), refuses the open as well, since it could be that file; only a path that does not exist is skipped. A write to a dangling symbolic link, which used to create the link's target wherever it pointed, is refused. A write that creates the file creates it only in the directory the check approved, on macOS and on Linux with `/proc`. On macOS the open itself refuses a link anywhere in the path. On Linux, where the open refuses a link only as the last component, a write first opens the checked parent directory, requires that descriptor's own path (`/proc/self/fd/<fd>`) to be the checked one, and creates the file through it (`/proc/self/fd/<fd>/<name>`), which the kernel resolves to the held directory whatever has since been swapped in at its path; a parent already swapped for a symbolic link is refused before anything is created. Elsewhere — Linux without `/proc`, and other systems — the open still follows a directory above the file swapped for a symbolic link between the check and the open, so a write that creates the file can create it, empty, where the link points, before the descriptor check refuses the write. The Gateway does not remove that file, and a refused write never deletes anything: Node has no `unlinkat`, so an unlink goes by name, and the same swap could redirect it onto a file that already existed, `install.json` included. The content and the truncation only ever go through the verified descriptor in any case, so nothing is written to that file and no existing file is emptied.
- When several offered options share the chosen kind, a refusal prefers the one that lets the worker continue (for example Codex `decline` over `cancel`).

Commands are checked as well:
- A permission request's `rawInput.command` and a `terminal/create` command line are refused under every policy when they name a protected path, as an error and without a prompt. That covers the literal path and its `~`, `$HOME`, `${HOME}` and quoted spellings, plus any path-looking word that resolves physically into one, such as `link/../.acp-gateway`.
- Since 1.8.0 a word with a `.acp-gateway` path segment, relative or absolute, that resolves into no protected path is never decided automatically. It may name the protected directory from a working directory the checks cannot see, such as `.acp-gateway/install.json` after a `cd ~`, or be only a search pattern, such as `grep -rn ".acp-gateway" src`. Under `ask` it is a normal prompt. Under `auto_approve` it is not approved or run on its own: a permission request goes to Main as a normal pending request, and a `terminal/create` as a pending request with its full command. `read_only` refuses it.
- Other commands keep the policy's normal treatment. `auto_approve` trusts commands inside the roots, because a shell command's file access cannot be verified from its text. These checks are best effort: a variable, a glob or a script the Worker wrote can always hide a path, which is why Gateway terminals also run in a sandbox (below).

Since 1.8.0 a terminal the Gateway opens for a Worker (`terminal/create`) is kept off the protected paths by the OS, because the daemon starts it outside any provider sandbox:
- On macOS it runs under `/usr/bin/sandbox-exec` with a profile that allows everything except reading, writing or connecting to the protected paths: a directory with everything under it, a file or the socket by name, each by its real path. The terminal's pid, process group, exit status, output and `terminal/kill` are the command's own. Setuid programs such as `ps` and `top` cannot start inside the sandbox. A command that cannot start there, missing or setuid, exits with status 71 and sandbox-exec's `execvp() of '<command>' failed` line in its output; before 1.8.0 a missing command failed to spawn instead.
- Where no sandbox is available (Linux and other platforms, or a `sandbox-exec` that cannot apply a profile, as inside another sandbox), `auto_approve` no longer starts terminals on its own: each `terminal/create` becomes a normal pending permission request with its full command. Writes stay automatic.

Since 1.8.0 a `fs/write_text_file` or `terminal/create` waiting for Main names the operation, and an approval covers only what it named:
- The pending request's `toolCall` (`toolCallId: "client-<requestId>"`) is, for a terminal, `kind:"execute"`, `title:"Run: <command line>"` (one line, cut at 200 characters) and `rawInput: {command, args, cwd, env}`; for a write, `kind:"edit"`, `title:"Write <path> (<n> bytes)"`, `locations: [{path}]` and `rawInput: {path, bytes}`, without the content. Each `env` entry is `{name, value}` for a variable that decides what runs, and `{name}` alone for any other, whose value may be a credential the Worker passes along. A variable decides what runs when it is execution-affecting (`PATH`, `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, `GCONV_PATH`, `NODE_OPTIONS`, `BASH_ENV` or any `DYLD_*`) or when the command line interpolates it (`$NAME` or `${NAME}` anywhere in the command or its args). A write or terminal that could not run anyway (outside the roots, protected, a cwd outside the roots, an `outputByteLimit` that is not a finite number of at least 1) is refused at once, before Main is asked and before anything is spawned or written.
- Main approving (`allow_*`) a Worker's `execute` request lets one later `terminal/create` through when it runs the same command, in the same working directory, with the same execution-affecting environment:
  - The command compares as an argv, word for word: the same number of words, each exactly the same. The approved command is `rawInput.command` or `cmd`. An array is the argv, and a string with `rawInput.args` is that string followed by the args. A string without args is a command line, and counts only when it is plain words: words separated by spaces or tabs, each either bare or wholly inside one pair of single or double quotes, which come off. Shell syntax (`;`, `&`, `|`, `<`, `>`, parentheses, `$`, a backquote, a backslash, `*`, `?`, brackets, braces, `~`, `=` or `#`), a quote that is not a whole word, an unclosed quote, or any blank other than a space or a tab makes the line opaque, and an opaque line, like a request that names no command, lets no terminal through. A `terminal/create` is the argv `[command, ...args]`. So a `sh -c` script, a login shell and a literal argv never stand in for one another: approving `["echo", "a; ./x"]` does not cover `sh -c "echo a; ./x"`, and approving `echo hi` covers the command `echo` with the argument `hi`, not `bash -lc "echo hi"`.
  - The working directory is the request's `rawInput.cwd`, or the session's when it names none, resolved like the terminal's, links included.
  - The execution-affecting variables, and the variables the command line interpolates, must have the same values in the terminal's `env` as in the request's `rawInput.env`: a terminal that changes one, or sets one the request did not, is asked about anew. Other variables are not compared.
  - A command that uses indirect (`${!NAME}`) or arithmetic (`$((…))`, `$[…]`) expansion is never covered, since the variable that decides what runs cannot be named in advance: each such terminal is asked about.
- Approving an `edit`, `delete` or `move` request lets one `fs/write_text_file` through to each file it named (`locations[].path`, `rawInput.path`/`file_path`/`notebook_path`), resolved like the write when Main is asked. A later write to a path that now leads to another file, through a link re-pointed since, is not covered.
- A write is bound to its canonical target as resolved when the write arrived, the path Main is shown (`rawInput.path`): it opens that target, not the Worker's path resolved again, and is refused, with nothing written or emptied, when the Worker's path no longer resolves to it, when the file that was there has been replaced by another (another inode), or when a new file would not be created at that very path. A Worker that re-points a link while Main decides therefore gets an error that names only the approved path, and can send the write again.
- Anything else, and a second run, is asked about anew with the full operation. Approvals end with the turn. Before 1.8.0 any approval let one write or terminal of the same kind through, whatever it was.
- A write or terminal waiting for Main counts its whole request as the Worker sent it, every field included whether it is used or not, against the session's pending-input byte budget, `maxPendingInboxBytesPerSession` (512 KiB). One that does not fit is refused with a JSON-RPC error to the Worker, and the bytes are released when it is answered or cancelled.

Claude sessions receive `_meta.claudeCode.options.disallowedTools` on `session/new` and on every restore. `read_only` adds `Bash`, `Edit`, `Write`, `MultiEdit` and `NotebookEdit`, and every policy adds path rules for the protected paths.

The Grok process is started with its cwd in a Gateway-owned directory (`ACP_GATEWAY_GROK_SANDBOX_DIR`, default `~/.cache/acp-gateway/grok-sandbox`) holding `.grok/sandbox.toml`, and with `GROK_SANDBOX=acp-gateway`:
- The profile extends Grok's `workspace` profile and denies every protected path to the whole process, through Seatbelt on macOS and Landlock on Linux.
- It covers Grok's in-process tools such as grep, which never reach ACP.
- Edits and terminals go through ACP and are unaffected by it; Grok's shell commands run in Gateway terminals, under the terminal sandbox above.

`permission_policy_partial` carries `scope`, the list of things the engine cannot enforce for that provider and policy: `edit_inside_roots`, `shell_write_inside_roots`, `read_outside_roots`, `read_protected`.
- Codex under `read_only`/`ask` has all four; under `auto_approve` it has the two read scopes.
- Grok has `read_outside_roots`.
- A consumer should treat any capability absent from `scope` as enforced, and anything listed as possible.

## Snapshot workspaces

`session_open {workspace:"snapshot"}` copies `cwd` twice, before the worker starts: a working tree and an untouched baseline, as clonefile/reflink copies where supported. The diff is baseline → tree, so later edits to the original never show up as reversed worker edits. A symlink inside the tree is re-pointed into the copy; one leaving the tree is not copied and is listed in `workspace.droppedLinks`. Protected directories are never copied, and a protected `cwd` is refused. The diff is capped at 64 MiB, beyond which it fails with `WORKSPACE_ERROR`. The copy lives under `ACP_GATEWAY_WORKSPACES`, default `~/.cache/acp-gateway/workspaces`, never under a protected path. The session's `cwd` is the copy, and the response carries `workspace:{mode,source,path}`. Direct sessions have no `workspace` key.

Symlinks are copied as links, and sockets/FIFOs are skipped. The copy is limited to 1 GiB and 200,000 entries; beyond that, or when `cwd` contains the workspace root, the open fails with `WORKSPACE_ERROR`. `additionalDirectories` are not copied. Since 1.8.0 all live copies together are also limited to 4 GiB, counted in the same measured source bytes as the per-copy limit (each copy is stored twice, as tree and baseline). Copies of open sessions, copies still being opened and deleted sessions' copies that are not gone yet all count. An open that would go past it fails with `WORKSPACE_ERROR` and `details: {bytes, usedBytes, limitBytes}` before anything is copied.

`session {action:"workspace_diff", sessionId}` returns `{changed, files, patch, patchBytes, truncated, patchArtifact?}`. `patch` is a `git diff --no-index` patch from the original (a/) to the copy (b/), with tree-relative paths, applicable with `git apply` in the original. It is capped at `maxInlineResultBytes`, with the complete patch as an artifact.

The engine never applies the patch. The copy is deleted on close and by session retention. It survives daemon restarts. A delete that fails is kept and retried by every maintenance pass, instead of being forgotten with the session record. Each copy holds an `owner.json` (beside `tree` and `base`, outside the worker's cwd) naming the Gateway state that made it. At startup and on every maintenance pass the engine deletes `ws-*` copies under the workspace root that carry its own marker and that no session references, such as a copy left by a crash between copying and registration. Copies without a marker or with another state's are never deleted, because daemons with separate state can share the default workspace root. A copy made before 1.8.0 is marked when a session that still references it is loaded.

## Caller identity

Since 1.6.0 a control request may carry `caller: {provider, sessionId, pid, instanceId}`. The control MCP server fills it once at startup from the agent CLI that spawned it: `provider` from the parent process name (`claude`, `codex`, `grok`, else `null`), `sessionId` from that CLI's exported id (`CLAUDE_CODE_SESSION_ID`, `GROK_SESSION_ID`, `CODEX_THREAD_ID`; Codex exports none to MCP servers, so `null`), `pid` of the parent, and a random `instanceId` per server process. Every Main on a machine shares one `rootId`; `caller` is what tells them apart.

- `openedBy` is the caller of the `session_open` or first `session_restore` that registered the session. Since 1.8.0 only an adoption rewrites it (see Per-Main isolation), keeping the previous value as `adoptedFrom`.
- `promptedBy` is the caller of the latest `prompt`, `run` or `task_prompt`. The same value is on that turn's `turn_start` event, so each turn names the Main its reply is for.
- Both appear on session responses, `session list`, and survive restarts. They are absent when the caller sent nothing (pre-1.6.0 control servers), so the old shapes are unchanged.
- Only `control` connections are recorded. An `observer`'s `caller` is not recorded; its `pid` still counts for the Worker check below. A malformed `caller` drops attribution, never the call.
- `sessionId` can go stale when the CLI switches sessions (for example Claude `/clear`) while the MCP server keeps running; `pid` and `instanceId` stay valid.

### Per-Main isolation

Since 1.8.0 the Gateway enforces what `caller` tells apart. A control request that carries a `caller` comes from a front-door Main and reaches only:
- sessions whose `openedBy` is that caller, by the `scope:"mine"` rule below (session ids decide when both sides have one, else `instanceId`);
- the tasks and inbox rows of those sessions. A task follows its session while the session record exists, then the Main that adopted the session (see below), else its own `caller`, because a handle outlives its session. An inbox row keeps its session's owner after the session is closed;
- records no Main is recorded for: sessions opened before 1.6.0 or by a client that sends no `caller`, with their tasks and inbox rows. Every Main shares these, as before.

Another Main's record answers as another root's does:
- `NOT_SESSION_OWNER` for every call that names its session: `session` get, check, workspace_diff, close, pin, unpin and clean, `config`, `poll`, `prompt`, `run`, `task_prompt`, `task_run`, `permission`, `answer`, `cancel`, and a `session_restore` that would reuse its record (unless the adopt rule below hands the record over);
- `NOT_TASK_OWNER` for `task_get`, `task_result`, `task_cancel` and a `run` attach (`{taskId}`), and `NOT_INBOX_OWNER` for `inbox get`;
- a link to its task is an unknown id (`INVALID_ARGUMENT`), and `ack` skips its task as `not_task_owner`;
- a task the caller can read (one on a shared session) never names it: its id is left out of that task's `parentTaskId` and `inputTaskIds`, and a key with nothing left is absent. A link to a task that no longer exists stays readable only to the Main that declared it.

Lists leave such records out and keep their shapes (an argument-free `task_list` stays unpaged): `session list`, `task_list`, `inbox list` and `attention`, setup's `sessions_stall_suspected` and attention alerts, and `subscribe` without `sessionIds`, which also never streams a session another Main opens later. `subscribe` with `sessionIds` needs every id to be reachable. `session clean` closes only the caller's own sessions, never the shared ones.

Requests without a `caller` keep root-wide access, unchanged. These are management requests (AgenLynk and other public-client consumers, `acp-gateway-admin`, installer health checks) and pre-1.6.0 front doors. Every observer keeps it too. `setup`, `gateway_config`, `provider`, `retention_preview`, `shutdown_if_idle` and `daemon_shutdown` stay root-level for everyone.

A Main is its CLI session. A front door restarted in the same CLI session (a new `instanceId`, the same `sessionId`) keeps its sessions. Each Codex thread is a Main of its own; a Codex front door that sends no thread id is one Main per process. A Main that comes back under another identity is another Main, for example a new CLI session, or a restarted front door that sends no session id (Auggie, Claude Code without `CLAUDE_CODE_SESSION_ID`, Codex calls without thread metadata). It takes its earlier sessions back by the adopt rule:
- Only `session_restore` adopts, and only a call that names an open record of its root exactly: `provider`, `acpSessionId` and the record's `cwd` (for a snapshot session, its copy or the directory it was copied from). `session list` and `get`, `poll`, `subscribe` and every other call keep answering as above.
- Only once the Main that holds the record is gone: no live control connection that sent its `caller` (a connection speaks for every `caller` it sent until it closes) and no live subscription of its. Root presence does not count, since every Main shares the root. While that Main is present, and for a `cwd` that does not match, the restore answers `NOT_SESSION_OWNER` and says nothing more. A daemon restart drops every connection, so a Main whose front door has not called (or resubscribed) since then counts as gone.
- A record no Main is recorded for is never adopted: it stays shared, and restoring it changes nothing about who may reach it.
- Adopting moves `openedBy` to the caller and keeps the previous one as `adoptedFrom`, which session responses carry wherever they carry `openedBy`, except polls. The record's tasks and inbox rows go with it, also once the session is closed, and its finished tasks become the caller's to receive: `attention` lists the unseen ones, collecting one marks it seen, and `ack` takes them. Each task keeps its `caller`.
- The restore then goes on as the owner's own would: a worker that is still connected answers `INVALID_ARGUMENT` (already registered, with `details.sessionId`), a busy session `SESSION_ACTIVE`, and otherwise the worker is restored.
- Repeating the restore changes nothing. An adoption is written with the next state snapshot (within about a second), not to the write-ahead log, so a Gateway crash in that window can hand the record back to its previous owner; the same restore takes it again. Closing an adopted session, by `session close` or by session retention, saves the adoption first: when the snapshot may not hold it yet, the snapshot is written and synced before the close is logged, so a crash after the close cannot hand the session's tasks and inbox rows back to the previous owner with no session left to restore. Without the write-ahead log the close and the adoption reach the same snapshot.

Management clients reach every record already and never adopt. An embedded `GatewayService` (no daemon) cannot tell whether a Main is gone, so it treats every owner as present and adopts nothing unless it is given `isOwnerLive`.

Like observer access, this is not a credential boundary: a process that holds the token can send any `caller`, or none. It keeps Mains that share a machine from reading, answering for, steering or cleaning up each other's work.

## Workers never get the Control

A Worker's own agent CLI can load the user's MCP configuration (Codex reads `~/.codex/config.toml` for the Workers the Gateway starts) and with it the Control MCP. Since 1.8.0 three checks keep the Control from a Worker:

- The Gateway sets `ACP_GATEWAY_WORKER=1` on every process it starts for a Worker: the provider process and each terminal it opens. A Worker cannot remove it from a terminal's env.
- The Control MCP server refuses to start inside a Worker's process tree: when that variable is set, or when an ancestor process is the daemon (its command line runs `gateway-daemon.js`, or it holds the daemon lock `<socket>.lock`). A daemon that died can leave its lock behind, naming a pid another process has since taken, so the lock's pid counts only when its command line runs the daemon or cannot be read. It also refuses when it cannot read its own ancestry on a host that should be able to (no `/proc`, and `ps` missing or blocked): it could not tell a Worker from a Main there, and a Worker could hide the daemon above it by blocking the lookup. A refused server exits with status 77 and a one-line reason on stderr, before it reads the identity or touches the socket. A Main's own server is never under the daemon, which is a detached child of the front door that started it.
- The daemon refuses a request whose `caller.pid` is, or runs under, the daemon or a process the daemon spawned for a Worker — a provider or one of its terminals — with `WORKER_CONTROL_DENIED`, before the connection binds or anything runs, `daemon_shutdown` included. It walks the caller's ancestry once, matching both the daemon's own pid and the live pids of the processes it spawned. The lookup happens on the first request that names a pid, and the verdict is reused only while the connection's `caller.pid` stays the same; a request that names a different pid is checked on its own. A connection that never names a `caller.pid` (management clients: AgenLynk, the admin CLI, installer health checks) is never refused for this. A spawned pid leaves the set the moment its child exits, so a later process that reuses the number is not refused. A walk that places the caller under none of them does not prove it is a Main, because the caller's pid, which the daemon does not control, may simply be gone; so the daemon then reads its own process entry, which it knows is alive. If that read fails too, the host cannot read ancestry at all (no `/proc`, and `ps` missing or blocked), no caller can be placed, and the request is refused with `WORKER_CONTROL_DENIED` and the message `Control access denied: caller process <pid> ancestry cannot be verified on this host`; if it succeeds, the caller runs outside and is served. On Windows, which has neither `/proc` nor `ps`, an ancestry that cannot be read is refused at neither end, so there a Worker is told apart only by the `ACP_GATEWAY_WORKER` variable, or by a pid that is itself the daemon's or one the daemon spawned. The daemon-pid match cannot count pid 1, which ends every chain, so when the daemon is pid 1 (a container entrypoint with no init) it cannot tell a Worker apart by the daemon's own pid; the spawned-process match still does, because a provider or terminal pid is a real child the caller descends from and never pid 1, and the `ACP_GATEWAY_WORKER` variable remains a backup.

`session_open` and `session_restore` refuse, with `INVALID_ARGUMENT`, a Worker `mcpServers` entry named `agent-acp` or `agent-acp-control`, or that mentions `acp-gateway-control`, `acp-mcp-bridge`, `gateway-daemon` or `control-mcp`; one whose env sets `ACP_GATEWAY_CONTROL_TOKEN`, `ACP_GATEWAY_ROOT_ID` or `ACP_GATEWAY_INSTALL_STATE` (ACP's `[{name,value}]` or an object); one whose command or arguments run a Control bin (`acp-gateway`, `acp-gateway-control`, `acp-mcp-bridge`), as a bare word (the command, or an argument as in `npx acp-gateway`) or a file of that name, or a file that resolves to a Gateway's `src/index.js`, such as `~/.acp-gateway/runtime/current/gateway/src/index.js`. In the command and arguments, a path the Gateway can look at (absolute, or under `~`) counts by what is there: a directory never counts, whatever its name, so a filesystem server may be rooted at a checkout called `acp-gateway` or `acp-mcp-bridge`; a file counts by its own name and what it resolves to, not by the directories it sits in. A path the Gateway cannot look at, one that is not there or a relative one (it resolves against the server's working directory, which the Gateway does not know), names a bin only as the command, which is never a directory; a relative path still counts whole as a mention. So as an argument `../acp-gateway` names no bin, while `../acp-mcp-bridge` still mentions one.

Like observer access, this is not a credential boundary: a process that holds the token and can start processes outside the daemon's tree is not stopped by it.

## Task links and scope

- `run`, `task_prompt` and `task_run` accept `parentTaskId` (the task this one follows up) and `inputTaskIds` (1 to 16 unique ids of tasks whose results went into the prompt). Every id must name a task the caller can see: on its root and, since 1.8.0 for a front-door Main, its own or one no Main is recorded for (see Per-Main isolation). Otherwise `INVALID_ARGUMENT` with `details.unknownTaskIds`, and nothing starts. The Gateway records them as declared and never infers links. `prompt` creates no task, so it refuses them, as does a `run` attach (`{taskId}`).
- Task reads carry `parentTaskId`/`inputTaskIds` only when declared. They survive restarts. Since 1.8.0 a front-door Main's reads leave out a link to a task it cannot see (see Per-Main isolation).
- `task_list` filters `parentTaskId`, `callerSessionId`, `callerInstanceId` combine with `status` and paging. Any of them selects the paged response.
- `scope:"mine"` on `session list` and `task_list` keeps records whose `openedBy`/`caller` is the requester: session ids decide when both sides have one, else `instanceId`. Records with no caller are nobody's. A Codex front door that sends no thread id matches by `instanceId`, so its threads are one Main. A request without a caller (observer, pre-1.6.0 front door) gets `INVALID_ARGUMENT`. Without `scope`, a front-door Main's lists hold its own records plus those no Main is recorded for (since 1.8.0), and management and observer lists hold the whole root.

## Idempotency and worker errors

A `run` whose `idempotencyKey` already names a run on the same session attaches only when the prompt, model and declared links digest match (input order aside). Otherwise it fails with `IDEMPOTENCY_CONFLICT`, and `details.taskId` holds the existing task. Changing `waitMs` or `resultBudgetBytes` on a retry is not a conflict. Runs recorded before 1.5.2 carry no digest and keep the old attach behavior.

A JSON-RPC error from the worker becomes `ACP_ERROR`, or `UNKNOWN_SESSION` for a `session/load|resume` of a session the worker does not know. The message keeps the historical `ACP error <code>: <message>` text, and `details.{method,acpCode,acpMessage,acpData?}` preserve the original.

## Adapter generations

A process is reused only while its provider definition (command, args including the adapter pin, env) is unchanged. After an adapter update, the old process keeps serving the sessions it holds, new sessions start a process of the current definition, and maintenance stops the old one when it serves nothing. Summary and full `setup` report `started` from real process liveness. `setup {provider}` adds `runningVersion` and `retiredProcesses`.

When `ACP_GATEWAY_STATE` points outside `~/.acp-gateway` and `ACP_GATEWAY_PROVIDERS` is unset, provider definitions and the registry cache live next to that state file. Reads fall back to the global definitions until the first write, which copies them.

## Retention preview

`retention_preview {values:{sessionRetentionMs,taskRetentionMs,inboxRetentionMs,resultRetentionMs}}` accepts any subset of those keys; direct top-level names are also supported. No deletion occurs. Unsupported policies such as artifactSessionLimit are rejected.

Response: `{ok,advisory:true,scope:"root",calculatedAt,configRevision,values,counts:{sessions,tasks,inbox,results},artifacts:{exact:false,reason}}`. Counts use the same predicates as GC and describe the records of the caller's root, every Main's included (retention is root-level), at the supplied policy. Active work and pending input are protected; pinned records are excluded from age retention while their session is open (since 1.8.0 a closed pinned session, and the records hanging off it, age out like any other). Task TTL is a separate, explicit handle lifetime and can still expire independently of pinning.

Preview is advisory: time, new work, references and settings can change before a restart/GC. Do not show it as an immutable deletion plan or a count covering other roots. Artifact reference protection prevents an exact byte/count forecast from age alone. Consumers should not invent artifact counts. In the normal single-user daemon, one root owns the engine's work.

## Replay and result integrity

`subscribe` returns the existing sessions/events/cursorTruncated fields and `replay`, keyed by session ID: `{complete,retainedTruncated,liveOnlyMissing,fromCursor,nextCursor}`. Message/thought chunks remain live-only; retained control/tool events remain bounded. A missing relevant raw chunk now also sets cursorTruncated, so older consumers cannot call that replay complete. Poll remains a retained-result/control view and does not treat intentional absence of raw chunks as poll history loss.

The replay is one reply, so since 1.8.0 it is bounded by bytes: half of `maxQueueBytes` (2MB by default) of serialized events across all sessions it covers. It is filled newest first, one event per session in turn, so one busy session cannot crowd out the others, and each session keeps an unbroken run of its newest events. A session whose older events did not fit reports it the way any incomplete replay does (`cursorTruncated` true, `complete` false), plus `budgetTruncated: true`, `omittedEvents` (how many matching events were left out) and `omittedBefore` (the first replayed sequence). Those events are still retained: `poll` with `cursor` set to `fromCursor` and `toCursor` set to `omittedBefore` reads them. A replay that fits has the same shape as before.

On client reconnect, `subscription_replay_truncated` still notifies callbacks of incomplete history. A gap/reconnect and healthy transport must never imply complete history. After daemon restart, the prior non-persisted event history is explicitly marked truncated. Fetch completed tasks through task_list/task_result and follow bounded artifact pointers for results; do not resubmit prompts to reconstruct a timeline. No persistent raw transcript journal is advertised.

At most 64 subscriptions per root. Invalid cursors fail before registration. Aborting a run wait releases its waiter immediately and leaves the worker running. Since 1.8.0 a long `poll` does the same: when its request is cancelled or its connection closes, the wait ends at once with `WAIT_ABORTED` and no response is built, so a result it would have carried is not counted as delivered. Only explicit task/session cancellation cancels the worker.

## Runtime identity and invariants

Full setup adds `runtimeRoot`, `gatewayBuildId`, `instanceId`, `sourceCommit`, `configRevision`, and `capabilities`. Build ID hashes the actual src JS file names/bytes at process start, cached for that process. It is not the archive digest or builder commit. Compare like identities; use instanceId to distinguish restarts. sourceCommit is taken from release manifest and null in a source checkout.

Required invariants and validation:

| Invariant | Gate |
|---|---|
| Work has a durable Task handle before ACP dispatch | crash matrix task-create barriers |
| Completed Task results survive restart or explicitly fail durability | result commit/artifact/fsync crash matrix |
| Unknown execution outcomes are not silently retried | restart recovery + idempotency tests |
| Observer cannot mutate or keep an owner alive | engine management + daemon RPC tests |
| Disabled provider cannot start a new registered session | actual public-client tests, including daemon restart |
| Shutdown cannot race a newly admitted open | engine admission race tests |
| Aborted readers free their budget without cancelling work | TaskStore/run cancellation tests |
| GC cannot remove active obligations or referenced artifacts | retention/resource/persistence tests |
| Unrecoverable event history is explicit | replay completeness tests |

Release builders require a v1.5.x tag (v1.5.0 through v1.5.2), v1.6.0, v1.7.0, v1.7.1 or v1.7.2 plus an independently supplied reviewed source SHA; verifiers require the same SHA. Existing v1.4.0's historical pin is retained. New archives use the public client and engine from the same source commit. Checksums and local unsigned build records are not signed provenance; the separate release workflow attests and verifies before publishing without overwriting assets.
