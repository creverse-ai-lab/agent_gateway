# Operations guide

[한국어](operations.ko.md) | **English**

Details on installer options, the update procedure, Worker control, and session and data management that the README does not cover. If you are installing for the first time, start with the Quick start in the [README](../README.md).

## Installing and updating

If a daemon from an earlier version is still running, the installer compares the version in the health response, replaces the daemon automatically, and then checks again. A manual upgrade that runs `git pull` and `npm ci` followed by `--install-all --refresh-registry` is therefore also supported.

To register several agents as orchestrator candidates, you can use `--target all`. This option puts a Control MCP with orchestrator permissions into each agent's configuration, so use it only with local agents you trust.

To review the installation plan again later:

```bash
acp-gateway-bootstrap --install-all --dry-run
```

How you update depends on how the Gateway was installed (see below). In a source checkout it is this one command:

```bash
acp-gateway-bootstrap --update
```

In a source checkout, `--update` fetches the upstream commit, installs and tests it in a temporary worktree (`npm ci`, then `npm run ci`), and only then fast-forwards the checkout. It also checks upstream changes to the ACP protocol and the official registry, and proceeds only once snapshot verification and the full automated test suite pass. It then prints the internal dry-run plan and updates the ACP registry, the adapters, and the MCP registrations. Finally, it restarts the running Gateway daemon on the new version and verifies the actual version. The installation state, the Control identity, and the front door selected at first installation are kept as they are. If the upstream check fails temporarily, it logs a warning but continues the local verification of the source it already fetched, and a test failure aborts the whole update before the daemon is replaced.

`--update` first works out how this Gateway was installed, from where its package sits. Only a source checkout (a directory with `.git`) is pulled and verified as described above. For an npm install (a package inside `node_modules`), `--update` runs neither Git nor npm: it checks the `latest` version of `acp-gateway-daemon` on the npm registry, reports `npm install -g acp-gateway-daemon@latest` when a newer release exists, and then goes straight on to the dry-run plan, the registry, adapter and MCP refresh, and the daemon restart. Install the new release first, then run `--update`:

```bash
npm install -g acp-gateway-daemon@latest
acp-gateway-bootstrap --update
```

An app-managed runtime (under `~/.acp-gateway/runtime/versions/`) reports `managed`: its app replaces the Gateway, and `--update` only refreshes this install's registrations.

The Claude Worker runs a Claude CLI you have installed, found in this order: `CLAUDE_CODE_EXECUTABLE` if it is not blank; otherwise the first executable `claude` in an absolute directory on the daemon's PATH, skipping copies inside the Gateway's own dependencies and any binary bundled with the Claude Agent SDK; otherwise `~/.local/bin/claude`. If none exists, Claude is reported as not installed. From 1.7.2, neither an npm install (with npm 10, 11 or 12) nor the GitHub runtime release includes the Claude Code binary that the Claude Agent SDK bundles; 1.7.1 already left it out of the runtime release and of npm installs made with npm 10 or 11.

To protect a user-modified `agent-delegator`, the skill is installed only on the first `--install-all` and is not touched by `--update`. `--install-skill` is also meant for first installation, so it does not automatically overwrite a copy that the installer already manages. To protect local source changes, the update aborts if the Git working tree is not clean, so commit or stash your changes first. The `npm link` that connects directly to the source does not need to be repeated after the first installation.

To apply only the latest default skill included in the current checkout, review the plan first and then update.

```bash
acp-gateway-bootstrap --update-skill --dry-run
acp-gateway-bootstrap --update-skill
```

`--update-skill` targets every `agent-delegator` copy recorded in the installer state, and it does not pull the Gateway source, change adapters or MCP, or restart the daemon. It replaces a copy only when the SHA-256 tree digest recorded at installation matches the currently installed copy, so a user-modified skill is preserved with a `customized` warning. A copy installed with v1.3.0 or earlier that has no digest is also preserved as `legacy-unverified`, even if its content is identical to the current default. Use `--update-skill --force` only when you want to overwrite with the default after reviewing the contents. To fetch the latest Gateway source first, run it as a separate command after `acp-gateway-bootstrap --update` succeeds.

### Host reconnection procedure

After upgrading the Gateway to a new version, you **must reconnect the host (Claude/Codex/Grok/Auggie) session** before the new tools and arguments become visible. An MCP host caches the tool list that the server first responded with for the duration of the session, and a daemon restart only replaces the socket (the RPC reconnects transparently), so the stale schema remains without any error. Bumping the server version does not break the cache.

Run the steps in order.

```bash
acp-gateway-bootstrap --update          # 1. Update the Gateway source, adapters and daemon
acp-gateway-bootstrap --update-skill    # 2. Update the skill (use --force if it was modified)
```

3. **Reconnect the host** — for Claude Code, use `/mcp reconnect` or start a new session; for Codex, Grok and Auggie, start a new session.
4. **Verify** — everything is fine if `agent_acp_run` is in the tool list and the `agent_acp_setup` response has no `staleFrontDoor`.

`staleFrontDoor` is a notice attached to `agent_acp_setup` and `agent_acp_session_open` responses when the version of the front door (the MCP process registered with the host) differs from the version of the running daemon, and it contains `frontDoorVersion`, `gatewayVersion`, the required `action` and, when the two versions can be ordered, a `reason`. With `reason: "front_door_older"` (or no `reason`), perform step 3. With `reason: "gateway_older"` the daemon is the older side, and reconnecting would only reattach to it: restart the daemon when idle with `acp-gateway-admin shutdown_if_idle` (it refuses while work is in flight, so retry later), and the next `agent-acp` call starts the front door's version. `acp-gateway-bootstrap --update` also repoints a managed `agent-acp` entry whose script is gone or that is a fixed path to an older Gateway, but only when the entry is provably the one this installer registered. From 1.7.2 the install state records the launch (command and args) of each registration and the names of its environment variables, and the entry must still launch exactly that, with exactly those variables; where they include the Control token and Main ID (an entry registered before 1.8.0), with the values `install.json` holds. Two differences are the installer's own and keep an entry its own: a token or Main ID variable that is gone (a run stopped between rewriting an entry and recording it), and `ACP_GATEWAY_INSTALL_STATE` set to exactly this install's `install.json` when that file is not at its default path. An entry whose env changed otherwise (a variable added, such as `HTTP_PROXY` or `NODE_OPTIONS`, one removed, or another token or Main ID) is kept with a warning, because replacing it would drop the change. An entry registered before 1.7.2 has no such record, and nothing tells it apart from an older Gateway install the user pointed it at, so it is never repointed automatically: unless it already launches this install, it is kept with a warning, and rerunning with `--force` once re-registers it and records its launch, after which `--update` moves it on its own. An entry that fails these checks is kept with a warning, and `--force` re-registers it. An entry that goes through a symlink another app manages is kept, with a warning if it resolves to an older Gateway, the link is broken, or the script behind it is missing. The agent CLIs have no atomic replace, so before removing an entry the installer reads its command, args and env; if the new entry then cannot be added, the previous one is put back exactly as it was. Since 1.8.0 that holds after `--rotate-token` too: no entry is ever given the new token, and a rotation that fails keeps the previous identity in `install.json` (see [Control identity and token rotation](#control-identity-and-token-rotation)). An update does not remove an entry it could not put back exactly (for example, when the CLI does not report its env); it keeps it with a warning, and `--force` replaces it anyway.

### Main installer options

| Option | Description |
|---|---|
| `--version`, `-V` | Show the currently installed ACP Gateway version |
| `--update` | After source pull, upstream check and full tests (source checkouts only; npm and app-managed installs skip Git) and a dry-run, update the Adapter, MCP and daemon — user skills are kept |
| `--install-all` | Install all Adapters, the Guide and the skill, then register Control with one front door |
| `--front-door codex\|claude\|grok` | Explicitly specify the Control MCP target of `--install-all` |
| `--install-control` | Install only the Control MCP for the orchestrator |
| `--install-guide` | Install only the read-only Guide MCP |
| `--install-skill` | Install the `agent-delegator` skill for the first time on discovered AIs — existing managed copies are preserved |
| `--update-skill` | Separately update only the unchanged installer-managed skills with the default from the current checkout |
| `--discover-agents` | Compare installed AIs against the official ACP registry |
| `--registry-agent ID` | Selectively install one registry agent, regardless of whether it was discovered |
| `--refresh-registry` | Ignore the 24-hour cache and refresh the official registry |
| `--offline` | Use only the stored registry cache |
| `--target codex\|claude\|grok\|auggie\|all` | Select the installation target of the Control MCP for the orchestrator |
| `--dry-run` | Print the plan without making actual changes |
| `--rotate-token` | Replace the Control token and the orchestrator identifier (Main ID) kept in `install.json` (see [Control identity and token rotation](#control-identity-and-token-rotation)) |
| `--force` | Explicitly replace unmanaged items or managed skills that the user modified |
| `--agent-auto-update on\|off` | Set ACP agent/adapter automatic updates, then restart the daemon |
| `--agent-update-notifications on\|off` | Set health check update notifications, then restart the daemon |

Skills are installed to Codex `~/.codex/skills`, Claude `~/.claude/skills`, Grok `~/.grok/skills`, and Auggie `~/.augment/skills`. Registry providers with no known dedicated path use the shared `~/.agents/skills`. If several providers use the same shared path, the skill files are copied only once, and the installer state records every one of those providers.

Control and Guide MCP registration supports Codex, Claude, Grok, and Auggie. In the default `--install-all`, Control is registered only with the one of Codex, Claude and Grok that the user selected as the front door, while the Guide and the skill are installed on all discovered supported agents. `--target` is kept for advanced manual targeting. The Control MCP has full control permission over the Gateway, so install it only on local agents you trust. Since v1.8.0 its entry no longer holds the token (see below), but a Worker whose own tools read files without going through the Gateway (measured with Codex, even under `read_only`) can still read the token in `install.json`, or in an entry an earlier installer wrote that still holds it, and act as a Main; see [Permission policies](../README.md#permission-policies) before giving such a Worker untrusted content. A Worker's own agent CLI can load the Control MCP from your configuration (a Codex Worker reads `~/.codex/config.toml`). Since v1.8.0 that server refuses to start inside a Worker's process tree: it exits with status 77 and one line on stderr, so the Worker's CLI may report `agent-acp` as failed to start. That is expected. It refuses the same way on a macOS or Linux host where it cannot read processes at all, not even its own (no `/proc`, and `ps` missing or blocked), because there a Worker cannot be told from a Main; its line on stderr then says that it cannot tell whether it runs inside a Gateway worker. The daemon likewise refuses a caller it cannot place with `WORKER_CONTROL_DENIED` ("ancestry cannot be verified on this host"). On such a host a Main can use the Control MCP again once `/proc` or `ps` is available. A process above it that this user may not see, such as the root-owned `sshd` above an SSH login on a Linux host whose `/proc` is mounted `hidepid=1` or `2`, does not keep a Main's Control MCP from starting, not even when it has taken the pid in a daemon lock (`<socket>.lock`) that a daemon which died left behind.

The official registry source is `https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json`, cached for 24 hours in `~/.acp-gateway/registry.json`. The execution definitions of discovered providers are stored in `~/.acp-gateway/providers.json`. `npx` and `uvx` distributions install the version pinned in the registry, while binary distributions use an already installed executable. An arbitrary AI that is not listed in the registry is not registered automatically, because its ACP execution contract cannot be inferred safely.

### Control identity and token rotation

The Control token and the orchestrator identifier (Main ID) are stored in `~/.acp-gateway/install.json` with permission `0600` and are reused across repeated installations. Since v1.8.0 that file is the only place the installer keeps them. The Control MCP entry is registered without them, and with `ACP_GATEWAY_INSTALL_STATE` only when `install.json` is not at its default path; the Control MCP reads them from `install.json` when it starts. `ACP_GATEWAY_CONTROL_TOKEN` and `ACP_GATEWAY_ROOT_ID` set in the entry's environment still take precedence. Neither the agent CLI's configuration nor the command line that registers the entry holds the token. Since v1.8.0 every installer write replaces `install.json` by rename and then empties the file it replaced if a hard link still holds it, so a hard link to `install.json` made earlier (a Worker can make one without being able to read the file) holds neither the token nor the Main ID once the installer has run, with or without `--rotate-token`, as far as the installer can empty the old file: not on Windows, which has no open that refuses to follow a link, nor when it may not open that file for writing, and a read of such a link through the Gateway is still refused for the token it holds. A write whose rename fails leaves the file as it was. The engine settings and the state snapshot are replaced the same way.

Since v1.8.0 a front door or the installer that starts the daemon hands it the token and Main ID on the daemon's stdin, not in its environment, which other processes of the same user can read (`ps -E`, `/proc/<pid>/environ`); Windows still uses the environment. A daemon you start yourself with `ACP_GATEWAY_CONTROL_TOKEN` set keeps taking them from there. If the hand-over fails, the daemon exits with status 78 and the reason (`DAEMON_IDENTITY_INVALID`) appears in the Control MCP connection error, as with a state recovery halt. Either way the daemon removes them from its own environment, so the processes it starts never inherit them; the rest of its environment still reaches Workers and their terminals (see [Permission policies](../README.md#permission-policies)).

An entry registered before v1.8.0 holds the token and Main ID in its environment. `--install-all`, `--install-control`, `--update` and `--rotate-token` re-register such an entry without them when it passes the ownership checks in the [Host reconnection procedure](#host-reconnection-procedure); one that launched an older Gateway is repointed at this install at the same time. Any other entry that still holds the token, such as one registered before 1.7.2, one whose environment changed since, or one that launches another Gateway install, is kept with a warning, and when the agent configuration that holds it is readable by other users, the installer makes that file `0600` (the Grok CLI writes its configuration `0644`). `--force` re-registers such an entry without the token. A run that took the token out of at least one entry ends with a warning that recommends rotating it, because copies made earlier, such as the agent CLIs' configuration backups (`*.bak`), still hold it. The installer never rotates on its own: apps such as AgenLynk keep the identity they read, and a new token would lock them out.

To rotate the token and Main ID, run the steps in order.

```bash
acp-gateway-admin shutdown_if_idle      # 1. Stop the Gateway once no work is in flight
acp-gateway-bootstrap --rotate-token    # 2. Write a new identity to install.json; the health check starts the daemon with it
```

3. **Reconnect** every host session (step 3 of the host reconnection procedure) and apps that keep the identity, such as AgenLynk. Each of them read the identity once, when it started, and the restarted daemon refuses the old one.

`--rotate-token` writes the new identity to `install.json` and re-registers no entry that reads it from there. Where the installer manages no Control entry, as in an install that an app such as AgenLynk manages, it registers none, and a dry run plans none; `--target` still registers the hosts it names. An entry that still holds a token is moved off it when it is provably this installer's, as on any update, and is otherwise kept with a warning that it holds the retired token, which stops working once the daemon restarts. A rotation that cannot update one of its entries is not committed: `install.json` keeps the previous identity, which the running daemon and every entry still share, and a retry completes it. Each entry the installer rewrites is recorded in `install.json` as soon as it is rewritten. A running daemon accepts only the identity it started with, which is why step 1 stops it. If it is still running, or a front door that still holds the old identity started it again in between, the health check in step 2 fails with `CONTROL_ACCESS_DENIED` although the new identity is already in `install.json`, and `acp-gateway-admin`, which reads the new identity, cannot stop it either. Then end the daemon with SIGTERM to the pid in `<socket>.lock` (an unconditional shutdown that also stops running Workers), and the next call starts it with the new identity.

### Monitoring ACP upstream versions

The maintainer checks the official ACP protocol repository and the registry manually with the commands below. When a protocol release or public wire version changes, or a registry agent is added or removed or its version or distribution information changes, update the snapshot, review it, and commit it to `dev`. Regular version updates for npm and GitHub Actions are managed by Dependabot as separate PRs targeting `dev`. Security updates target the default branch, `main`, under GitHub policy.

```bash
npm run monitor:check   # If there are changes, print a report and return exit code 2
npm run monitor:update  # Update the review snapshot to the current upstream state
npm run monitor:sync-dependencies  # Sync the ACP adapter versions that the repository includes directly
npm run update:upstream  # Manual maintenance path that runs the update above and the full CI at once
```

When the maintainer runs `npm run update:upstream`, the snapshot update, the synchronization of the pin and lockfile of the managed ACP adapters, and the full CI can all be done locally in one go. This command does not commit or push automatically. Review the protocol and registry changes and the test results with `git diff`, then commit to `dev`. For regular users, `acp-gateway-bootstrap --update` does not modify repository files arbitrarily; it reports upstream changes and safely updates only the runtime adapters.

The two update paths have different roles.

- **ACP agent/adapter versions:** The daemon periodically checks the versions pinned in the official registry and updates automatically. Running `acp-gateway-bootstrap --update` also immediately re-reads the registry and performs the same update.
- **ACP protocol wire version:** A new major version is detected and flagged as a warning in the `monitor:check` report, but it is not applied automatically. After compatibility testing, you must change `src/acp-version.js` and the monitor configuration together.
- **Gateway npm dependencies:** Review the lockfile and the CI results in the Dependabot PR before merging.

The current runtime uses ACP wire version 1. `schema/v2` in the official repository is also detected, but it is not marked as v2 support and there is no automatic switch. A snapshot update is a notification and a starting point for review; it does not perform an automatic merge or a Gateway release.

Since v1.1.0, the daemon checks the official ACP registry at startup and every 24 hours afterward. If a discovered `npx` or `uvx` adapter has a newer version, it is installed automatically and the provider definition is updated. Worker processes that are already running are not interrupted, and the updated adapter applies from new processes or sessions. Binary distributions that must be installed manually are not replaced automatically and are left as a health warning. Since v1.8.0 every command the installer runs, including these installs, is stopped after 10 minutes and reported as timed out, and only the first and last 512KB of what it prints on each stream are kept, with the number of bytes left out marked in between. A daemon that is asked to stop while an update is still running waits for it at most 5 seconds, then aborts it, which stops its `npm`/`uv` process, and goes on to stop its workers and save its state; the next start checks again. When that happens the daemon says so on stderr.

The `agentUpdates` field of the `agent_acp_setup` health response contains the check time, the applied versions, the remaining manual updates, and errors. When notifications are on, `alerts` in the same response contains messages to show to the user. In other words, the Gateway does not push anything to the screen on its own; the orchestrator relays the notifications to the user when it receives the health check result. To check again immediately, call setup with `refreshAgentUpdates: true`.

The Gateway itself is never pulled or installed automatically. On the same cycle, a source checkout checks only the `package.json` version published on the remote `main` of its Git repository, and an npm install checks only the `latest` version of `acp-gateway-daemon` on the npm registry. If a higher version exists, `gatewayUpdate` in health (which carries `installMode`) and the `gateway_source_update_available` alert direct you to run `acp-gateway-bootstrap --update` for a source checkout, or `npm install -g acp-gateway-daemon@latest` followed by `acp-gateway-bootstrap --update` for an npm install. An app-managed runtime checks nothing and reports `status: "managed"`; its app updates it. As a result, the installed Gateway, the installation state, and custom skills do not change until the user explicitly updates.

Automatic updates and notifications are on by default. After installation, you can turn each off or back on as follows, and custom skills are not changed.

```bash
acp-gateway-bootstrap --agent-auto-update off
acp-gateway-bootstrap --agent-update-notifications off

acp-gateway-bootstrap --agent-auto-update on
acp-gateway-bootstrap --agent-update-notifications on
```

The Dependabot configuration must exist on GitHub's default branch to be activated, and the remote `dev` branch must be kept for PRs targeting `dev`.

### Publishing to npm (maintainers)

The Gateway is published to npm as `acp-gateway-daemon` (the command names stay `acp-gateway-*`). Publish only a commit whose release version is already in `package.json`, `package-lock.json`, `GATEWAY_VERSION` in `src/version.js` and the newest heading of both changelogs; `npm run ci` checks that they agree. npm versions are immutable: a published version number can never be reused, even after an unpublish, so a mistake is fixed only by a new version.

- **GitHub Actions (the usual path):** Push the release tag, then run the `Publish npm` workflow (`.github/workflows/publish-npm.yml`, manual `workflow_dispatch`) on that tag with the input `version`, for example `gh workflow run publish-npm.yml --ref v1.8.0 -f version=1.8.0`. The run fails unless it was dispatched on `refs/tags/v<version>`, the input equals the `package.json` version and `GATEWAY_VERSION`, the package name is `acp-gateway-daemon`, and the checked-out commit is the tag's commit (a tag moved after the dispatch is refused). It refuses a version that is already on npm. In a job that cannot publish, it installs with `npm ci --omit=optional`, runs `npm run ci` and `npm run smoke:npm` (npm 10, 11 and 12), and packs through `scripts/pack-release.js`, failing unless the packed tarball's sha256 equals that of the tarball the smoke test installed; a second job, the only one allowed to request a GitHub OIDC token, runs no repository code and publishes exactly that tarball with npm 11 (`npm publish --provenance --access public`).
  - Publishing uses npm trusted publishing (OIDC): no npm token is stored in the repository or used by the workflow. On npmjs.com, `acp-gateway-daemon` → Settings → Trusted Publisher must list GitHub Actions with organization `creverse-ai-lab`, repository `agent_gateway`, workflow filename `publish-npm.yml`, no environment, and allowed actions that include `npm publish`. A configuration created after 2026-09-03 allows only `npm stage publish` unless `npm publish` is also ticked, and this workflow runs `npm publish`. The fields are case-sensitive and npm does not check them when you save; a mismatch shows up only as a failure in the publish job (for example `ENEEDAUTH` or `E404`). Renaming the workflow file stops publishing until that setting is updated.
  - With trusted publishing working, set Settings → Publishing access to "Require two-factor authentication and disallow tokens"; trusted publishing keeps working and a leaked token can no longer publish.
  - npm attaches provenance only for a public GitHub repository, and trusted publishing needs a GitHub-hosted runner, so the workflow cannot publish while the repository is private.
- **Local publish:** From a clean checkout of the release tag, install with `npm ci --omit=optional`, run the checks, log in and publish. The package bundles `node_modules` as installed, and `npm publish` runs the `prepack` guard (`scripts/pack-release.js`), which refuses a tree that is not exactly the locked production tree; do not pass `--ignore-scripts`. This path publishes without provenance.

```bash
git clone --branch v1.8.0 https://github.com/creverse-ai-lab/agent_gateway.git
cd agent_gateway
npm ci --omit=optional
npm run ci
npm run smoke:npm
npm login
npm publish --access public
```

Publishing to npm does not replace the GitHub runtime release (`acp-gateway-runtime-darwin-arm64.tar.gz`) that the desktop app installs. That release is still built separately by the `Release runtime` workflow and keeps the package name `acp-gateway`; publishing one does not produce the other.

## Worker parameter control

`agent_acp_config` queries and changes the session parameters that a Worker exposes directly through ACP `configOptions`. Check the possible values and the current value with `action: list`, then, while the session is not working, pass `action: set`, `configId`, and `value`. On ACP wire v1, selectable string settings and boolean settings are supported, and categories such as `model`, `mode`, `model_config`, and `thought_level` are preserved as they are.

The Gateway does not invent and pass values such as `temperature` or `max_tokens` that the Worker does not expose. The supported range therefore depends on the options that each ACP adapter, such as Claude, Codex or Grok, actually advertises. A settings change is recorded as a `config_changed` session event, so a future DAG orchestrator can choose parameters according to each node's task type, cost, and quality policy and track them together with the results. For a Worker that pins the model per process, do not change the model in an existing session; open a new session instead.

## Result retrieval and artifacts

Since v1.3.0, the poll default is lean. While a turn is in progress, `result` is omitted automatically (it is included only when you explicitly set `includeResult: true`), and after completion, `result.text` in a poll holds only the **final answer segment** (the message text after the last work boundary), not the accumulated transcript. Retrieve progress narration with `includeInspection: true`. `includeTranscript: true` on `get` of `agent_acp_session` returns the bounded transcript that remains in memory, and the full transcript that overflowed is retrieved by following `resultArtifact`. You can also query the retained event history by range with `cursor`/`toCursor`/`eventTypes`. For the detailed retrieval path, follow the "Retrieve the correct result" table in the `agent-delegator` skill.

All data beyond the inline limit is spilled to a file in `~/.acp-gateway/artifacts`, and the response carries a truncated preview and a pointer (path, byte count, and whether it is complete) — a tool event payload over 4KB (UTF-8) becomes `dataArtifact`, a final answer over 64KB becomes `textArtifact`, and a transcript over the memory limit (1MB) becomes `resultArtifact`. Only content within the limit is kept inline, so RAM and the orchestrator context do not grow with the size of the result. Artifacts are limited to 100MB per file and 512MB in total, of which the last eighth (64MB) only durable Task results may fill, so that transcripts, terminal output and tool event payloads cannot leave a finished result with nothing but its preview. Files referenced by a live session are retained through the 24-hour cleanup. When a newer update of the same tool call replaces a `tool_call_update` whose payload was spilled, the older file is deleted at once unless a poll, a subscription (live or replay) or a session `get` already handed its path out; one that was handed out ages out with the rest. Since v1.8.0 a Worker cannot read or overwrite an artifact through the Gateway's file requests (`fs/read_text_file`, `fs/write_text_file`) under any name, a hard link it made inside its roots included, and an artifact the Gateway deletes while such a link holds it is emptied first, so the link keeps nothing. Concurrent unanswered permission and question requests follow a safety limit of 64 per session, and a large description chunk is handled as is within the 32MB protocol frame limit. Transport, session, and Main budgets are also reported together in `setup().resourceLimits` — a write queue of 4MB per control connection and a 10-second no-progress limit (the queue on the worker stdin side is derived from the concurrent request limit), a 1MB prompt, a 500KB file read (in bytes; the excess is reported as truncated through `_meta["acp-gateway/read"]`), 10MB of terminal output, and 64 sessions per Main and 1000 processed inbox history entries.

## Sessions and data

- State files (schema v5): `~/.acp-gateway/state.snapshot.json` (full state) + `~/.acp-gateway/state.wal.ndjson` (control transition log)
- Since v1.8.0, `~/.acp-gateway/state.json` (the v4 format) is no longer written. A leftover one is still read and migrated at startup, then deleted once a synced v5 snapshot holds its contents. A 1.4 to 1.7 Gateway still reads the v5 files after a rollback, though it serves a large Task result only as its preview (marked `resultDegraded`); a Gateway older than 1.4 finds no state and starts empty. The v5 files need no conversion, but the Control MCP entry may: one that the 1.8 installer wrote or rewrote holds no token, and a 1.7.x front door reads the token only from its entry's environment, so it will not start from such an entry. Once the installed package is the 1.7.x build, run that build's `acp-gateway-bootstrap --install-control --target <host> --force` for each host that holds such an entry, then reconnect those host sessions (step 3 of the [Host reconnection procedure](#host-reconnection-procedure)). The 1.8 installer cannot do this: it never puts the token back, `--force` included. Without `--force`, the 1.7.x installer leaves an entry that still launches the right script as it is.
- While state changes, the full snapshot is rewritten at most about once a second when the WAL is on, and also on every WAL rotation and on shutdown. The WAL records themselves are written immediately, as before. Since v1.8.0 every one of these snapshots is fsynced before it replaces the previous one, and its directory after the rename.
- Idle resumable sessions are unloaded after 30 minutes by default
- When the Gateway ends a Worker's provider process (at shutdown, when its idle sessions are unloaded, once an adapter update has replaced it and it serves no session, or after a transport failure such as a provider that stops reading its input), it sends SIGTERM and, if the process is still running 2 seconds later, SIGKILL. The terminals the Worker opened are ended the same way: on macOS and Linux each with its whole process group, on Windows the terminal process itself. Before v1.8.0 a provider that ignored SIGTERM kept running.
- A terminal starts in the directory it was approved for and no other, even when a Worker swaps that directory for a link right before the start: on Linux with `/proc` it starts in a descriptor of that directory, and on macOS (and Linux without `/proc`) it starts as a short `/bin/dash` script that checks the directory it changed into and only then execs the command. A terminal whose directory changed there runs nothing and exits with status 75. The script passes the terminal's environment on except variables whose names are not shell names, such as exported bash functions, and sets `PWD` and `OLDPWD`. It never runs under another shell, because bash takes code from the environment: a host with neither `/proc` nor `/bin/dash` starts the terminal by path right after checking the directory, as before, so a swap in between can still move the command there.
- Results and events are retained for 24 hours by default
- Session resume checkpoints are retained for 7 days by default, and the bytes of a Task handle are retained for 24 hours by default (`ACP_GATEWAY_TASK_RETENTION_MS`)
- Use `pin` for sessions that need to be kept for a long time. A pin protects a session only while it is open: a closed pinned session ages out like any other.
- Response bodies, thoughts, and the full event history are not persisted in the state file. A Task result larger than `ACP_GATEWAY_WAL_INLINE_RESULT_BYTES` is kept in the snapshot as a reference to its artifact plus a short preview, the same form the WAL uses, so the snapshot does not grow with retained transcripts.
- Results and terminal output beyond the inline limit are stored temporarily in `~/.acp-gateway/artifacts` and cleaned up according to the result retention period
- The control socket is `ACP_GATEWAY_SOCKET`, by default `acp-gateway-<uid>.sock` in the OS temporary directory (per user on macOS, the shared `/tmp` on most Linux systems), with its lock file `<socket>.lock` next to it. The daemon creates it with permission `0600` and never with wider bits. Since v1.8.0 a client connects only to a socket owned by the same user whose whole directory chain is the user's own (or root's) and writable by no one else, unless a directory is sticky like `/tmp`; anything else fails with `SOCKET_UNTRUSTED` before the token or anything else is sent. This closes an intermediate-directory swap that an owner check of the socket alone would miss (an `lstat` follows an intermediate symlink but refuses a final one): Node cannot read the connected peer's identity without a native addon, so a path no other user can rewrite stands in for it. The daemon makes the same check before it touches anything at the path (the lock file, the probe and removal of a stale socket, the bind) and, rather than put its socket where another user could swap a link for it, refuses to start — recording `SOCKET_UNTRUSTED` in the recovery marker and exiting with status 78 — so a hand-set `ACP_GATEWAY_SOCKET` must be in directories that you or root own and no one else can write, a sticky one such as `/tmp` aside. A socket directory that does not exist is not reported as untrusted: no daemon can be running there, so `daemon_shutdown` and `shutdown_if_idle` answer that the Gateway is already stopped (`alreadyStopped`), and any other call starts the daemon, which does not create the directory and so refuses to start as above; that call then reports `SOCKET_UNTRUSTED` from the recovery marker. The client and the daemon check one path only, the canonical one: each resolves the socket's directory, links and `..` included, and uses the socket's name in that real directory for the check, the connect and the bind, never the path as written, whose links the kernel would resolve again at each use, after whoever owns one could have pointed it elsewhere. Keep a hand-set path short: it is the canonical path that has to fit in a Unix socket address, 103 bytes on macOS and 107 on Linux (counted in UTF-8), and on macOS a path in the temporary directory resolves 8 bytes longer, under `/private`. A longer one fails with `SOCKET_PATH_TOO_LONG` before anything is sent, `daemon_shutdown` and `shutdown_if_idle` included, and the daemon refuses to start on it, recording `SOCKET_PATH_TOO_LONG` in the recovery marker and exiting with status 78. Before, Node cut such a path short on some systems, so the daemon listened at another path and clients could not find it. On a Linux host shared with other users, one of them can still occupy the default path and keep the Gateway from starting: set `ACP_GATEWAY_SOCKET` to a path in a directory only you can write, such as `$XDG_RUNTIME_DIR/acp-gateway.sock`, everywhere a client runs (the env of the `agent-acp` MCP entry, apps, `acp-gateway-admin` and the installer)
- Copies of damaged state files that a failed start sets aside for an operator (`state.wal.ndjson.corrupt-<time>`, `state.snapshot.json.downgraded-<time>` and so on) are limited to the newest three per file and reason, and deleted after 7 days. Temporary files that a crashed writer left next to the state and settings files are removed at the next start.

### Status, interruptions and attention

Since v1.7.0 the Gateway reports where delegated work stands instead of leaving the orchestrator to guess. None of it cancels or re-runs anything for you.

- **Status reason and stall hint** — Session `get`/`list` carry `statusReason`, `statusChangedAt` and `lastWorkerActivityAt`, and `stallSuspected` when a running turn has sent nothing for `stallHintMs`. `setup` raises `sessions_stall_suspected`.
- **Interruptions** — A task the Gateway cut short carries `interruption: {reason, executionOutcome, at}`, where `executionOutcome` is `not_started` or `unknown`, and its result lists `next` steps. From v1.7.2, only a task created by v1.7.2 or later can be judged `not_started`; an older task interrupted from then on is `unknown`, and a `not_started` that v1.7.0 or v1.7.1 already recorded on an older task reads as `unknown`, with its `next` rebuilt. `agent_acp_session {action: "check"}` reports whether a session is `restorable`, `restorable_with_caveats`, `not_restorable` or `unknown` without starting a provider.
- **Attention** — `agent_acp_inbox {action: "attention"}` returns `needsMain` (pending requests, `stale` after `attentionStaleMs`) and `updates` (finished tasks whose result has not reached the Main that started them). `{action: "ack", taskIds}` marks the listed tasks as seen.
- **Scope** — `scope: "mine"` on `agent_acp_session {action: "list"}` and on `task_list` keeps only the calling Main's records. A front door that sends no caller identity (pre-1.6) gets `INVALID_ARGUMENT`. Since v1.8.0 a Main's lists without `scope` already leave out other Mains' records (see below); `scope: "mine"` also leaves out the records no Main is recorded for.
- **Quarantine** — After `maxConsecutiveRestoreFailures` failed restores in a row, `prompt`, `task_prompt`, `run` and `config` fail with `SESSION_QUARANTINED` without contacting the provider. `check`, `agent_acp_session_restore` (which restores the Main's own record in place, also while its provider is off, and lifts the quarantine on success) and `agent_acp_session_open` remain available.

### Per-Main isolation and recovery after a restart

Since v1.8.0 each orchestrator (Main) that calls through the Control MCP reaches only the sessions it opened, with their tasks, requests and results, plus sessions no Main is recorded for (opened before 1.6.0, or by a tool that names no Main). Another Main's session answers `NOT_SESSION_OWNER` (its tasks `NOT_TASK_OWNER`, its inbox rows `NOT_INBOX_OWNER`) and is left out of lists, and `clean` closes only the caller's own sessions. Clients that name no Main, such as AgenLynk, `acp-gateway-admin` and the installer's health check, and every observer still reach the whole Gateway. The budgets counted per Main ID (`ACP_GATEWAY_MAX_SESSIONS_PER_ROOT` and the other `_PER_ROOT` limits below) are shared by every Main that uses that ID; isolation does not split them. This keeps cooperating agents apart and is not a security boundary against a process that holds the Control token. The full contract is in the [Management API](management-api.md#per-main-isolation).

A Main is its CLI session: a Claude Code or Grok session, or a Codex thread. A front door restarted inside the same CLI session keeps its sessions. A new conversation is a new Main, and so is a restarted front door that sends no session id (Auggie, Claude Code without `CLAUDE_CODE_SESSION_ID`, Codex calls without thread metadata). Its earlier sessions are then missing from its lists. Take each one back instead of opening a duplicate:

1. Find the session's `provider`, `acpSessionId` and `cwd`. Every `agent_acp_session_open` and `agent_acp_session_restore` answer carries them. Otherwise read them from a view that lists every session on the Gateway, such as AgenLynk, or call `session {action: "list"}` through the public client without a `caller`; `acp-gateway-admin` has no session listing.
2. From the new Main, call `agent_acp_session_restore` with exactly those three values. Nothing else moves a session: not list, get, poll or a subscription.
3. The restore takes the session only once the earlier Main is gone, that is when no open Control connection has spoken for it and none of its subscriptions is live. A daemon restart ends every connection. One Codex process serves all of its threads over one connection, so a thread cannot take over another thread's session while that Codex process still runs. While the earlier Main is there, or when `cwd` does not match, the answer stays `NOT_SESSION_OWNER`.

The session then carries `openedBy` (the new Main) and `adoptedFrom` (the earlier one). Its tasks and pending requests go with it, and its finished runs whose result the earlier Main never received become the new Main's to collect: `agent_acp_inbox {action: "attention"}` lists them. Repeating the restore is harmless. The adoption reaches disk with the next state snapshot, within about a second, so a crash before that can hand the session back to the earlier Main, and the same restore takes it again. Closing an adopted session, or session retention removing it, saves the adoption first, so a crash right after the close cannot hand its tasks and requests back to the earlier Main. If that save fails, for example because the state directory no longer accepts new files, the close still answers as a close and ends the Worker's session, but the Gateway keeps the session, closed, until the adoption is saved: `agent_acp_setup` reports persistence as unhealthy meanwhile, the session can no longer be prompted or configured, and the next maintenance pass (every 5 minutes by default), close or clean saves the adoption and removes the session. A crash before that can bring the session back to the earlier Main; the same restore then takes it again, with its tasks and requests. The `agent-delegator` skill walks a Main through the same steps.

### Durability and recovery

Task creation and result finalization are appended to the WAL and fsynced before the response is returned. That is, a Task handle that Main has received survives a daemon crash, and after a restart an incomplete Task is finalized as `failed` (with a restart message). Since v1.7.0 it also carries `interruption` (see below). The remaining transitions (permission and question records, session registration/termination, state changes) use a 5ms group commit. Since v1.7.2, a failed session restore (the failure count, a quarantine and `lastRestore`) and a successful restore that ends a failure streak are also fsynced before the response is returned, so a crash neither undoes a quarantine nor brings back one that a success lifted. If that synced write fails, the restore's outcome stands but is reported: persistence becomes unhealthy, `setup` raises a `STATE_RESTORE_NOT_DURABLE` warning, which the next successful write does not clear, and the restore's answer carries `durability: { persisted: false, errorCode: "PERSISTENCE_UNHEALTHY" }` (in `details.durability` of the error when the restore failed). A Task result larger than `ACP_GATEWAY_WAL_INLINE_RESULT_BYTES` is written to an artifact that the WAL record references. Since v1.8.0, when that artifact cannot be written (the artifact quota or the disk is full) and the WAL therefore holds only the result's preview, the commit that follows reports this instead of clearing it: persistence stays unhealthy, and `task_result` and `agent_acp_run` carry `durability: { persisted: false, errorCode: "PERSISTENCE_UNHEALTHY" }` beside the whole result, until the next state snapshot, which holds the whole result, has been written (normally within about a second). A crash before that brings the Task back with its preview only (`resultDegraded`). On macOS, Node does not expose `F_FULLFSYNC`, so only `fsync(2)` is used — an abnormal process exit is fully protected, and a power loss exposes only the group commit window (5ms by default).

Since v1.8.0 a WAL append that fails, for example on a full disk, leaves the log as it was: the log is cut back to its last whole record, and the record's sequence number goes to the next one that lands, so a restart never meets a gap or a damaged record in the middle of the log. A log that cannot be cut back takes no further record, and persistence stays unhealthy, until a WAL rotation replaces it, which the next state write starts at once: the rotation writes and syncs a snapshot first, then replaces the log. Every snapshot, including the one written about once a second while state changes, is fsynced before it replaces the previous one, so a power loss cannot leave a torn snapshot as the base the log replays onto. The state directory is locked against a second Gateway (`STATE_DIR_LOCKED`) and against a second state store for it in the same process, and a lock left by a Gateway that died is claimed so that two Gateways starting at once cannot both take it.

If the state file is corrupted, the daemon **does not silently start with an empty state** and aborts instead. At that point it records the reason in `~/.acp-gateway/state.recovery-required` and exits with exit 78, and its contents are surfaced in the Control MCP connection failure message. A copy of the damaged file is kept next to it (see the retention limits above). Recovery is chosen explicitly.
